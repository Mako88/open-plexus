Does an EXACT store scale with data where the superposed one does not?
======================================================================

Script: experiments/g11_04_scaling_exponent.py, --chars axis, --slots arm
Status: DISPATCHED, awaiting results.


IN PLAIN TERMS
---------------
Our model squashes everything it learns into one big pile of numbers added on
top of each other. g11-05 showed that giving it sixteen times more text to read
makes no difference at all — it has stopped learning from text — while a normal
model keeps improving. The suspicion is that the adding-together is what breaks
it: once things are summed, the individual pieces cannot be pulled back out.

The exact cache is the one part of this model that does NOT add things together.
It keeps a bounded number of items separately, so a read can pick one out rather
than average over everything.

**So: does the part that keeps things separate improve with more text, when the
part that sums them does not?** If yes, the adding-together is identified as the
thing that is broken, rather than merely suspected — and it argues for building
the distributed version out of machines that each hold a few whole items instead
of each holding a slice of one big pile.


WHY THIS IS THE MEASUREMENT g11-05 DEMANDS
-------------------------------------------
g11-05 measured both our arms flat on data: -0.0008 and -0.0010 against a
backprop control of -0.0243 at R2 0.96. The architecture is saturated on data as
well as width, so "we are just small" is gone as an explanation.

The through-line says why: the store holds a bigram count table (note 033,
cosine 0.9455), a real bigram model scores 3.583 bits where we score 5.5, and
more text sharpens counts whose information is destroyed before the readout sees
them. **A bottleneck downstream of the statistics cannot be widened by improving
the statistics.**

That is an inference, not a measurement. This sweep tries to make it one:
the same model, the same data axis, with a component that does not sum.


A STRUCTURAL FACT DISCOVERED IN THE PRE-DISPATCH CONTROL, AND IT MOVES THE
PREDICTIONS
---------------------------------------------------------------------------
**The cache is reset on every `run` call, and `run` is called once per 128-token
chunk.** So it is a within-sequence working memory, not a long-term store. It
cannot accumulate across the corpus; the only thing that persists between chunks
is the readout `Wo`.

This was not introduced by the retrieval seam — the cache arrays were always
allocated inside `run`. It was simply never stated, and it changes what a flat
cache exponent would mean. Written down here BEFORE the run, because discovering
it afterwards would make any explanation of the result unfalsifiable.


PREDICTIONS
------------
Registered before dispatch.

  P1  THE CONTROL FIRES: backprop |b| > 0.02 on data. **This is admissibility,
      not evidence.** g11-05 already measured -0.0243 for this exact arm at this
      exact width, so it is close to known; it is listed because a grid whose
      reference does not move cannot be read, and that has happened once.

  P2  REPLICATION: `single` at width 64 is flat, |b| < 0.02, and its 250,000
      cell lands on g11-05's 5.505. Same script, same settings, same arm --
      disagreement is a dispatch or identity error, not a finding.

  P3  THE CACHE ARM IS ALSO FLAT. **This is the pessimistic prediction and the
      one I would bet on**, on the structural fact above: a cache that resets
      every 128 tokens cannot accumulate anything from a larger corpus, so the
      only path by which more data could help is the readout -- and g11-05 says
      the persistent path does not improve with data.

  P4  THE CACHE'S ADVANTAGE IS A CONSTANT, NOT A SLOPE. Against the
      state-matched arm it holds roughly 0.15-0.25 bits at every data size,
      rather than widening or closing. The pre-dispatch control measured 0.146
      at 30,000 characters and the published result is 0.244 at 250,000, so a
      mild widening is possible; a CLOSING gap would refute this.

WHAT WOULD REFUTE EACH: P1 by |b| < 0.02 on backprop. P2 by a non-flat single
arm or a 250k cell away from 5.505. P3 by the cache arm reaching |b| > 0.02.
P4 by the gap changing sign or collapsing.

**THE INFORMATIVE OUTCOME IS EITHER WAY, WHICH IS WHY IT IS WORTH THE MATRIX.**

  If P3 is REFUTED -- the cache scales where the sum does not -- the sum is
  IDENTIFIED as the binding constraint rather than inferred. It also argues
  directly for partitioning the distributed model by ITEM rather than by
  DIMENSION (decision 61), since the cache is that architecture at one machine's
  scale.

  If P3 HOLDS, the flatness lives in the PERSISTENT path, and a per-chunk cache
  cannot reach it however well it works within a sequence. The next mechanism is
  then obvious and specific: **make the cache persist across chunks**, which is
  also what a distributed item-sharded store would be.


COST
-----
20 jobs: 5 data points x 4 arms, two seeds inside each on 2 workers.

    chars      62,500  125,000  250,000  500,000  1,000,000

    arm               width  slots   numbers held
    single               64      0          4,096
    cache128             64    128         20,480
    single-matched      143      0         20,449
    backprop             64      -              -

**The state-matched arm is the control that makes this a comparison.** A cache
is not free state, and measuring "with cache" against "without" at equal width
compares a bigger model to a smaller one -- the mistake g10-08 made with width,
and g10-09 made with a cache and was RETRACTED for. Width 143 holds 20,449
numbers against the cache arm's 20,480.

Slot count 128 is taken from the hybrid-store result (commit 88c9c12), at width
64, where it was measured at 5.344 against a state-matched 5.499. Naming the
cell a pinned value came from is the habit note 028 bought.

PRE-DISPATCH CONTROL, measured locally at 30,000 characters, seed 1:

    arm              width  slots  numbers    bits    secs
    single              64      0     4096   5.513    13.8
    cache128            64    128    20480   5.336    28.6
    single-matched     143      0    20449   5.482    69.4
    backprop            64      -        -   4.482     2.3

The cache is CONNECTED at these settings and the state-matched control
reproduces the published shape: 0.146 bits over an equal-state superposed store.

Cost is linear in chars, so from the MOST EXPENSIVE CELL per g11-03's rule:
`single-matched` at 1,000,000 characters is 2.31 ms/char = ~2,310 s per seed,
two seeds on two workers, so ~39 minutes of wall clock against a 300-minute
timeout. Summed over all 20 jobs the matrix is ~123 minutes of local-equivalent
job time; g11-05's runners came in FASTER than local, so this is an upper bound.


MEASURED ON
------------
Tiny Shakespeare, 64 symbols, 1,003,854 training characters available, so the
top of the range uses essentially all of it and the axis spans 16x. The script
refuses rather than truncating if a cell asks for more than the corpus holds.

80/20 fit/calibration split within the capped stream. Tested on the corpus's
held-out tail, which is the same text at every point on the axis. Temperature
fitted on held-out training text for our arms; the backprop arm's logits are
used raw, since fitting a temperature for it would flatter it.

The arm name and the cache must agree: a `cache` arm without slots, or any other
arm with them, is refused. A `single` arm carrying slots would record itself as
`single` and be averaged into the same column as the no-cache arm -- two
different models under one name, running cleanly, announcing nothing.
