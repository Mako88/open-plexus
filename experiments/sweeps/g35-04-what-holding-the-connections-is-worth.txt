What is holding the connections worth?
======================================

Script: testbed/run.py --mode bucket --walk   (driver: tools/bucket_drive.py)
Status: RUN, local, 2026-07-31, Docker 29.6.1. **P1 was registered in `g35-03`
        before `Link` existed**, which is where it is scored.

ANSWER: **almost exactly 2x on an impaired link, and P1 held.** A grounded
question falls from 10.19 s to **5.09 s**; the load phase from 449.79 s to
226.21 s. Every identity check still passes.


IN PLAIN TERMS
--------------
The first version opened a fresh connection for every single message. That is
like redialling before each sentence of a phone call: on a fast line nobody
notices, on a slow one it doubles everything.

Now a machine opens one line to each of its peers and keeps it. The work is
identical and the answers are identical; it just stops paying to say hello.

That halves it. A question that took ten seconds takes five.

**Five seconds is still too slow**, and the remaining cost is a different thing
entirely: the sheer NUMBER of small questions each machine has to ask before it
can answer. That one needs a change to the method, not to the plumbing.


MEASURED ON
-----------
Docker 29.6.1, four node containers plus a driver, `tc netem` on every container
including the driver. Same shape as `g35-03` shape B so the two are comparable:
6 concepts, 60 occasions, 19 surfaces, bucket width 50, derived bound,
`conditional`.


PREDICTIONS
-----------
Registered in `g35-03` before `Link` was written:

    P1  Holding connections should bring the 10.2 s per walk UNDER 6 s -- better
        than half, because the setup is a full round trip of the two.
        REFUTED IF it does not, which would put the cost in the message COUNT
        rather than the per-message overhead.


COST
----
Load 226.21 s, walk 96.69 s impaired. Clean: load 1.11 s, walk 0.46 s.


RESULTS
-------
    phase   link              one connection per message    held connections
    load    clean                                  3.86 s              1.11 s
    walk    clean                                  1.36 s              0.46 s
    load    delay 40ms/10ms                      449.79 s            226.21 s
    walk    delay 40ms/10ms                      193.65 s             96.69 s

    per grounded question, impaired               10.19 s              5.09 s

`agrees_with_one_process` and `walk_agrees_with_one_process` are **true in every
cell**, before and after. `driver_reconnects` is **0**, so nothing went stale
during these runs and the retry path is untested by them.


SCORECARD
---------
  P1  HELD. 10.19 s to **5.09 s**, under the predicted 6 s. The ratio is 2.00 on
            the walk and 1.99 on the load, which is what removing one of two
            round trips per message should give and is a good sign that nothing
            else changed.

            **The refutation clause did not fire, and that matters for what
            comes next**: the cost was NOT dominated by the message count, so
            attacking the count is still available and still untried.

  Clean runs improved by MORE than 2x — 3.5x on the load, 3.0x on the walk —
  because on a fast link the connection setup is a larger share of a cheap
  message. That is the less interesting direction and is reported so the 2x is
  not mistaken for a universal figure.


WHAT THIS DOES NOT SETTLE
--------------------------
**5.09 s a question is still outside John's accepted latency.** `g24-01`
measured 161 ms a round over held connections and the ruling took depth 10 at
about 3.2 s. This is a single grounded question.

**The remaining cost is the message COUNT**, which `g33-03` measured as one peer
read per candidate partner, scaling with fan-out rather than with `k`. The
untried fix is a local prefilter — rank cheaply by raw count, which needs no
peer, then pay for the top `m` only — and `g33-03`'s P1 already registers it,
including the measured reason to doubt it: under skew, `g32-02` found 60 of 60
rare surfaces had a different concept's surface as their best raw-count partner.

**The retry path is unexercised here.** `driver_reconnects` is 0 in every run, so
the stale-socket handling that connection reuse made necessary has unit tests and
no field evidence.
