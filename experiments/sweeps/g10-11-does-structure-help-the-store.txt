Does structure in the data give superposition a crossover?
==========================================================

Script: experiments/g10_11_does_structure_help_the_store.py
Status: RUN. Seconds, local, one budget.

ANSWER: NO. **g10-10's compression hypothesis -- which I wrote one run earlier --
        is REFUTED.** Capacity is KEY-limited, not information-limited, so
        compressible data buys the store nothing.

        And a second finding nobody was looking for: **the store cannot
        overwrite.** Rebinding a cue superposes rather than replaces, and
        repeated rebinding destroys it completely.


IN PLAIN TERMS
---------------
The previous run guessed that the blended store looked bad only because our test
data is deliberately random, and that it would do better on data with real
patterns in it.

It does not. Making the data far more repetitive does not help the store at all,
because what limits it is how many different *questions* it must tell apart, not
how much information the answers contain.

And re-answering the same question repeatedly does not update the store -- it
piles the answers on top of each other until none can be read.


THE RESULT
-----------
Reported as **accuracy divided by chance**, because the conditions contain
different numbers of distinct values and therefore have different floors.

      items            random        few values          few cues
         16              16.0               7.0               8.6
         64              58.7               6.4               0.0
        128             108.4               4.5               0.0
        256             117.7               3.3               0.0
        512              98.8               2.8               0.0

**Random is 99x chance at 512 items; eight prototypes is 2.8x.** Structure in the
values makes the store *relatively worse*, not better. Note 020's `sqrt(d/N)` law
is about separating KEYS, and shrinking the answer set does not shrink the number
of keys.

**`few cues` is 0.0 everywhere past 16 items**, and that is not noise.


PREDICTIONS -- WRITTEN BEFORE THE RUN
---------------------------------------
The script's docstring registered the doubt as well as the hypothesis:

> If capacity is key-limited rather than information-limited, then compressible
> data buys the store nothing and g10-10's explanation is wrong.

**That branch fired.** The hypothesis was mine, one run old, and stating the

THE ERROR CAUGHT BEFORE PUBLICATION, FOR ONCE
-----------------------------------------------
The first version reported RAW accuracy: random 0.207 against few-values 0.350 at
512 items, and printed *"fewer distinct values helps, the compression story
stands"*.

**The conditions have different chance levels.** Eight prototypes means guessing
scores 0.125; four thousand values means guessing scores 0.00024. Comparing 0.350
against 0.207 compares two numbers measured against floors five hundred times
apart, and the conclusion inverts once that is fixed.

This is the sixth instance this session of *a number measured on one thing
applied to another*, and **the first one caught before the write-up rather than a
cycle later.**


THE SECOND FINDING: NO OVERWRITE
----------------------------------
`few cues` binds the same 8 cues repeatedly, each time to a fresh value. Only the
most recent binding is meaningful, and the store returns **0.0x chance** for it.

The store accumulates: `memory += outer(value, key)`. Rebinding a cue adds
another term rather than replacing the first, so retrieval returns the sum of
every value ever bound to that cue, and the argmax of a sum of unrelated vectors
is noise.

**A table overwrites in one line.** This is a third structural difference from a
cache, alongside capacity and exact recall, and it was not on note 030's list of
four.

> **CORRECTED: "cannot overwrite" was measured at `decay=1.0`, which I chose.**
> The g9 line's default is 0.997 and the model supports any value. Rebinding 8
> cues, accuracy against a chance of 0.00024:
>
>        decay   64 rebindings   512 rebindings
>          1.0           0.250            0.000
>        0.997           0.125            0.000   <- the g9 default
>         0.99           0.125            0.375
>         0.95           0.875            0.750
>
> **It CAN overwrite, at decay 0.95.** What it cannot do is overwrite at the
> decay this project actually uses. So the finding holds for every configuration
> measured here, and the mechanism is not missing -- it is priced.
>
> **And the price is retention.** Decay 0.95 has a half-life of about 13 steps
> against 0.997's 231. Overwriting and remembering are the same dial pulled in
> opposite directions, which is a sharper statement than "cannot" and is the one
> that belongs in any comparison with a table -- a table does both at once and
> pays nothing.


It also raises a question about the g9 line worth asking separately: MQAR and
`reward_recall` present each cue ONCE per sequence, so no result in this project
has ever depended on rebinding. **Any workload that revisits a key is outside
what has been measured.**


WHAT THIS DOES NOT SAY
------------------------
It does not say superposition is useless -- it says superposition's capacity is
set by key separation, which is a known law being confirmed rather than a
verdict. The properties that might still favour a store are untested and are now
down to one: **slicing by dimension where the two are competitive intact**, which
requires a task neither structure trivially wins, and none exists.
