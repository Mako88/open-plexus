A bounded per-key cache that does not reset
===========================================

Script: experiments/g10_06_a_cache_that_persists.py
Status: RUN. Counting only, seconds, local.

ANSWER: persistence buys a CACHE up to 1.48 bits where it bought the vector
        store almost nothing. At 32 slots -- affordable by `slot_cost.py` -- a
        cache scores 4.153 against the model's 5.734 on the same stream.


IN PLAIN TERMS
---------------
An earlier run found the device cannot use a longer memory: given eight times as
much context it captured a quarter of what was available. That ruled out
"remember for longer" as a fix **for that device**.

But the reason it was ruled out does not apply to a lookup table. Clearing a
table is not a saving; the device clears its memory because of how it is built,
not because clearing helps.

So: the same bounded table, never cleared. It improves enormously, and it ends up
substantially better than the device on exactly the same text.


WHY IT WAS WORTH ASKING
-------------------------
[g10-04](g10-04-does-context-help-this-model.txt) ruled out persistence, and it
ruled it out **for the vector store**. [g10-05](g10-05-how-many-slots.txt) reset
its cache at every chunk boundary because that is what the model does. Neither
asked what a cache does when it is simply not cleared, and a cache has no reason
to clear.

John's third question is whether traditional computing -- caches, DHTs -- can
replace biological mechanisms. A bounded per-key table with vectors regenerated
from token ids is exactly that: an LRU table, the most conventional structure
available.


PREDICTIONS -- A DECISION RULE, WRITTEN BEFORE THE RUN
-------------------------------------------------------
Three branches, in the script before it was executed:

    the cache reaches the bigram        -> an LRU table with derived keys meets
                                           the bar this project set for goal 2
    within 0.5 bits of it               -> a conventional cache gets most of the
                                           way where the vector store gets none
    still more than 0.5 bits short      -> persistence helps a cache where it
                                           could not help the vector store, and
                                           is not sufficient alone

**The second branch fired**, and the fairness caveat below means the first was
never really available -- which is a flaw in the rule as written rather than a
finding. The rule compared against the bigram, and the bigram is not the
comparison this run can fairly make. That was not noticed until the numbers were
in front of me.

I did NOT predict the size of the effect. Had I, the honest guess would have been
well under +1.48 bits, because g10-04 had just measured persistence being worth
almost nothing on the same axis -- to a different mechanism.


THE RESULT
-----------
      slots   persisting    reset each 256   persistence buys
          1        6.006             6.113             +0.107
          2        5.680             5.893             +0.212
          4        5.277             5.659             +0.382
          8        4.850             5.475             +0.626
         16        4.457             5.381             +0.924
         32        4.153             5.349             +1.197
        128        3.867             5.349             +1.482

    for reference   the model 5.734    bigram (all training text) 3.711

**Persistence is worth up to 1.48 bits to a cache.** The same axis was worth
0.24 bits to the vector store across an eightfold context increase, of which it
captured 24%. The mechanism, not the axis, was the problem.


THE COMPARISON THAT IS FAIR, AND THE ONE THAT IS NOT
------------------------------------------------------
**FAIR: cache against the model.** Both run over the same test stream using only
prior tokens. At 32 slots the cache is **1.58 bits better than the model**, and
`slot_cost.py` puts 32 slots at 2,752 token ids -- cheaper than a width-16 node's
own store of 4,096.

**NOT FAIR: cache against the bigram.** The bigram is fitted on disjoint TRAINING
documents and cannot see the test set's own repetition. The cache adapts online
and exploits exactly that. So *"within 0.155 bits of the bigram"* overstates it,
and part of that closeness is online adaptation rather than knowing English.

Stated here rather than buried, because it is the number a reader would quote.


WHAT THIS MEANS, AND WHAT IT DOES NOT
---------------------------------------
**It is an uncomfortable result for the vector store**, which is why it is worth
having. On this task, at this scale, the conventional data structure beats the
biological one by 1.58 bits at a lower memory cost -- and the thing that makes it
affordable, regenerating vectors from token ids, is the same `derived_keys`
property the whole g9 line already rests on.

**It is not a result about AGI or about the gating line.** A cache holding the
last N successors of every character it has seen is closer to a bigram with
bounded counts than to a memory. It cannot bind, cannot be gated by a late
signal, and has nothing to say about `reward_recall`. Reaching a language bar
this way is not the model learning anything, and the honest reading is that
**character-level text may simply be the wrong task to justify an associative
store** -- not that the store is worthless.

That is a question about which task earns which mechanism, and it is a better
question than the one this line started with.

WHAT WOULD REFUTE WHAT
-----------------------
- persistence buys a cache little   -> the vector store's failure was not
                                       specific to it. NOT OBSERVED: +1.48 bits
- the cache loses to the model      -> superposition was not the limit after all.
                                       NOT OBSERVED: 1.58 bits the other way
- an affordable cache cannot do it  -> it needs 128+ slots and stops being a
                                       tiny-node mechanism. PARTLY: 128 slots is
                                       11,008 ids, above a width-16 store, while
                                       32 slots at 2,752 is below it and gives up
                                       0.29 bits
