Does concept partitioning escape G5's wall?
============================================

Script: experiments/g5_01_scaling.py, with `concept_nodes` in place of `partitions`
Status: NOT RUN. Predictions registered and committed before the run.

ANSWER: pending.


IN PLAIN TERMS
---------------
The project's biggest recorded failure is that splitting the work across more
machines stops paying: to handle a problem ten times bigger you need each machine
six times wider, and the number of machines you can usefully use falls to a third.
That is the opposite of the premise, which is that machines are the thing you can
add more of.

But there are TWO ways to split the work, and only one was ever measured.

**By dimension:** every machine holds a slice of the width and every answer is a
fragment, summed across machines. That is what was measured, and the sweep that
measured it says in its own words that the splitting is what causes the wall.

**By concept:** every machine holds the WHOLE width for the facts it owns, and an
answer comes from one machine rather than from a sum. Nothing about it has ever
been measured at scale.

So the failure may be a failure of the arrangement the project no longer intends
to use.


WHY THIS EXISTS
----------------
`g5-01`, in its own words:

    256 dimensions in one piece solve seq 384. The same 256 dimensions split
    sixteen ways reach 0.769. **The wall is caused by the partitioning, not by
    the underlying rule.**

That is DIMENSION splitting. `peer.py` describes the other arrangement: *"2
messages per read against 2N"*, no sum, the read served by the one node holding
the fact from a full-width store.

**Grepped `experiments/sweeps/` for `concept_nodes`: no file mentions it.** The
verdict in `GOALS.md`'s gate ladder rests on a grid that never ran the arrangement
`note 081` calls mandatory.

**Both arrangements were smoke-tested against this grid's config before this file
was written** -- neither hits the six `concept_nodes` combination refusals, because
g5-01 uses no hops, no `memory_cap`, no `consolidation` and no `leave`.


THE MEASUREMENT
---------------
`g5_01_scaling.py`'s grid unchanged -- widths 16 to 256, sequence lengths 48 to
384 -- with `concept_nodes=n` where it currently sets `partitions=n`. The fitted
exponent is the quantity: how fast the width needed grows with sequence length.

    g1-10   unpartitioned                exponent 0.37
    g5-01   dimension-partitioned        exponent 0.69
    this    concept-partitioned          ?


PREDICTIONS
-----------
  P1  THE TEST. The concept-partitioned exponent is BELOW g5-01's 0.69.

      Refuted if it matches or exceeds it, which would mean the wall is about
      splitting the STORE at all rather than about splitting the WIDTH -- and
      would close the last cheap doubt about #10's ❌.

  P2  It does NOT reach g1-10's unpartitioned 0.37.

      Concept partitioning still divides the facts, so a node sees fewer of them
      and the walk crosses machines. Matching the unpartitioned exponent exactly
      would be too good and should be suspected before it is believed.

  P3  THE GATE. The concept-partitioned arm SOLVES seq 384 at width 256, where
      the sixteen-way dimension split reached 0.769.

      This is g5-01's own comparison, which is the sharpest single number in it.
      If both arrangements reach 0.769 the difference does not exist at the size
      where g5-01 found the wall, and P1's exponent is decoration.

  P4  THE ONE I EXPECT TO BE WRONG. The exponent's confidence interval will be
      wide enough that P1 cannot be settled at this grid's resolution.

      `g5-02` and `g5-03` are both calibrations for fitting an exponent through
      points that were bounds, and `g5-01` fitted through a grid whose arms
      pinned at edges. **If the interval straddles 0.69, this run has not
      answered P1 and must say so rather than quoting a point estimate** -- which
      is the failure those two sweeps exist to prevent.


WHAT WOULD MAKE THIS NOT COUNT
--------------------------------
**Reading a point estimate as an answer.** The interval is reported or the run is
not reportable. `tools/summarise_scaling_exponent.py` already exists and
`g5-03`'s calibration is that a tool can be UNDER-confident as easily as over.

**A different quantity wearing the same name.** `134` measured pooled capacity as
IDENTICAL between the arrangements at equal per-node memory, and lone-node
capacity differing 16×. Those are capacity, not retrieval quality under length.
Neither predicts this exponent, and neither may be quoted as if it did.

**Knobs carried.** The learning rate grid, seeds and epochs stay exactly g5-01's,
so the arms differ only in how the store is split.


COST, MEASURED RATHER THAN ESTIMATED
--------------------------------------
**One cell -- width 256, seq 384, one seed, one learning rate -- exceeded TEN
MINUTES locally and was killed.** That is `CLAUDE.md`'s own line for what belongs
in Actions rather than on the machine, and it is the calibration `g8_05` earned:
a thing described as "a quick control before the full run" that held the machine
for over ten minutes was an experiment.

So the full grid -- 5 widths x 4 lengths x seeds x learning rates, TWICE for the
two arms -- is CI work and is not being run locally. At the measured 8x
local-to-runner factor a single cell is over an hour on a 2-vCPU runner, so the
grid needs sharding by seed as g5-01's own workflow does.

The decisive single cell is running in the background instead, because
`g5-01`'s sharpest number is one comparison rather than a curve: sixteen-way
dimension splitting reached **0.769** at exactly this cell.
