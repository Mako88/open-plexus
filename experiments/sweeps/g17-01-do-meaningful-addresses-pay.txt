Do addresses that mean something pay for themselves, and what do they cost?
==========================================================================

Script: experiments/g17_01_do_meaningful_addresses_pay.py
Status: **NOT DISPATCHED.** Calibrated locally first, and the calibration says
        the instrument cannot answer the question yet.

ANSWER: **THE FLOOR IS AT THE FLOOR.** The model does not learn word-level text
        at all in its current configuration, so there is nothing for an index to
        improve on and every arm would return the same non-answer.

        This is decision 63's rule arriving from the usual direction -- probe the
        bottom of a range before spending a matrix on it -- and it saved the
        matrix.

MEASURED ON
------------
Tiny Shakespeare (`data/tinyshakespeare.txt`), WORD level via `corpus.words`,
min_count 10, vocabulary 1733, 183,655 training words. Width 128, pair keys,
`derived_keys`, one epoch, chunk 256. Bits per word on the held-out tail, with
temperature fitted on held-out TRAINING text.

One seed. This is a calibration, so a single seed is the right spend: the
question was whether there is any headroom at all, and 1.40 bits below a unigram
is not a margin that seeds would move.


THE CALIBRATION
----------------
Tiny Shakespeare at word level, min_count 10, vocabulary 1733, width 128,
pair keys, one epoch. Bits per word on held-out text, temperature calibrated on
held-out TRAINING text:

    uniform (knowing nothing)                     10.759
    train 10,000 words                            10.750
    train 30,000 words                            10.733
    train 90,000 words                            10.721
    word unigram (knowing word frequencies)        9.323   <- NOT APPROACHED

**Ninety thousand words buys 0.038 bits, and the model is 1.40 bits WORSE than
counting how often each word appears.** More data moves it 0.01 bits per tripling.
There is no headroom here for a mechanism to occupy.

Single-token keys instead of pair keys **diverge to NaN**: the store has no decay
and no cap in this configuration, and at word level the same key recurs often
enough for the norm to run away. That is a second, separate reason the instrument
is not ready.


WHY, AND IT IS NOT A TUNING PROBLEM
------------------------------------
Note 034 measured the price of pair keys at character level: distinct keys go
from `vocab` to the number of pairs that actually occur -- 469 against 66 in 4000
characters, a sevenfold increase.

**At word level that multiplier explodes.** A 1733-word vocabulary over 90,000
words produces tens of thousands of distinct pairs, most seen once or twice, so
almost every key the store is asked about at test time was written at most once
during training. The store is not superposing a reusable structure; it is
memorising hapaxes.

So the two obvious repairs pull opposite ways, which is why this is a real
problem rather than a knob:

  - **Pair keys** give context and destroy recurrence.
  - **Single-token keys** give recurrence and diverge, and carry note 033's
    bigram ceiling besides.

Neither was measured at word level before, because nothing in this project had
run at word level before.


WHAT THIS DOES NOT SAY
-----------------------
**It says nothing about note 045.** The index was never reached. P1 through P5
remain registered and unscored, and the design is neither supported nor refuted
by anything here.

It also says nothing about the content vectors themselves: P4 passed on this
exact corpus, and `king -> richard, edward, henry` is not in doubt. The structure
is there. What is missing is a model that can use it.


WHAT IT COSTS TO FIX, AND THE HONEST OPTIONS
---------------------------------------------
1. **Make the model learn word-level text.** The real fix and the expensive one.
   It is its own line of work -- decay, cap, key scheme, learning rate -- and
   note 045's question would wait behind all of it.

2. **Measure the index where the model already works.** MQAR and the relational
   tasks are solved by this model, but their entities are arbitrary by
   construction, so there IS no similarity for an index to find. Running there
   would measure an index over noise.

3. **Build a task with designed similarity, where the model already works.**
   Entities that genuinely share attributes, with the model in a regime it
   handles. The mechanism gets isolated, the control is free -- the same index
   built over shuffled structure must fail -- and it does not wait on (1).

**(3) is the choice**, and it is the same move MQAR was for the store: a task
where the property exists by construction and the model is known to work, so a
null result is about the mechanism rather than about the instrument.
