G0 step 3 (partial) -- what does ONE content lookup buy?
=========================================================

Script: experiments/g0_03_induction.py
Status: RUN. Prediction 4 -- the real one -- held emphatically: 0.180 -> 1.000.
        Prediction 2 REFUTED, and in the opposite direction to the risk flagged.


IN PLAIN TERMS
--------------
The untrained network scores at chance on our memory test. We think we know why:
it has no way to look something up by content. It can only blur everything it
has recently seen together.

So this bolts exactly one lookup operation onto the same untrained network --
"find the last time you saw this symbol, and report what came next" -- and
changes nothing else. Same network, same reader, same data.

If the score jumps, we have located the missing ingredient precisely, and we know
the room in our test is actually reachable rather than theoretical. If it does
not jump, our explanation for the failure is wrong and we need a different one.

Important: the lookup is hand-written, not learned. So a high score does not mean
anything learned. It means the door is not locked.


QUESTION
--------
docs/notes/006 §7 takes a requirement from the literature: what separates
architectures that solve MQAR from those that cannot is INPUT-DEPENDENT sequence
mixing, not capacity. g0-02 supports the capacity half -- doubling the substrate
from 64 to 128 units bought 0.008.

Does adding a single input-dependent lookup to the same frozen substrate close
the gap?

Conditions, all with the readout fitted on training sequences and scored on
held-out ones:

  frozen        substrate alone                     (g0-02 baseline: 0.180)
  +lookup-state substrate + state at the position following the last
                occurrence of the current token
  +lookup-token substrate + one-hot of the TOKEN at that position
  lookup-only   the lookup feature WITHOUT the substrate


PREDICTIONS -- written before the run
--------------------------------------
1. +lookup-token scores near 1.000. On this task the token following the last
   occurrence of a key IS that key's value, so this is close to an upper bound.
   It is included to confirm the wiring, not to be impressive.

2. +lookup-state scores well above the 0.344 trivial floor but clearly below
   +lookup-token. The state at that position has to be DECODED rather than read,
   and it has been mixed with everything else the substrate held at the time.
   Guess: 0.55-0.85.

3. lookup-only scores close to +lookup-token. If the substrate contributes
   almost nothing once the lookup is present, that is worth knowing -- it would
   mean the whole result is the lookup and the substrate is carrying no
   information the readout can use.

4. The jump from frozen to +lookup-state is LARGE -- at least +0.3. This is the
   real prediction. It is the one that would confirm docs/notes/006 §7 on our own
   generator rather than by analogy from other architectures.

5. The advantage survives more pairs. At n_pairs=8 the frozen substrate is at
   0.143 and the floor at 0.234; the lookup conditions should stay far above
   both, because a lookup does not care how many pairs there are.

Most likely to be wrong: (2). The state-mode variant might land near chance,
because the substrate state at the value position is a blur of everything up to
that point and the specific value may simply not be linearly recoverable from
it. If so, that is informative rather than disappointing -- it would say the
lookup has to fetch something cleaner than a mixed state, which is a real
architectural constraint and one we would rather know now.


WHAT WOULD REFUTE WHAT
-----------------------
- +lookup-state ~= frozen        -> input-dependent mixing is NOT the missing
                                    ingredient; docs/notes/006 §7 does not
                                    transfer to this substrate and the
                                    explanation for g0-02 is wrong
- +lookup-token well below 1.0   -> the lookup is misimplemented, since it
                                    returns the answer by construction
- lookup-only ~= +lookup-state   -> the substrate contributes nothing
- advantage shrinks with n_pairs -> the lookup is exploiting something about
                                    small K rather than doing retrieval


WHAT THIS DOES *NOT* ESTABLISH
-------------------------------
G0 step 3 proper is still NOT done, and this must not be reported as if it were.

The lookup is HAND-SPECIFIED. Nothing learned it. A high score shows the headroom
is REACHABLE and localises what reaches it; it does not show the task is
LEARNABLE end to end. Those remain different claims, and only a model trained
from scratch on this generator settles the second.

What this does buy is a sharper version of the remaining question. If one
hand-written lookup closes the gap, then "is MQAR learnable" narrows to "can this
lookup be learned" -- which is a much better question to spend a transformer on.


RESULT
------
240 training / 160 held-out sequences per condition.

condition       floor    frozen  +lookup-state  +lookup-token  lookup-only
--------------------------------------------------------------------------
reference       0.344     0.180          1.000          1.000        1.000
n_pairs=8       0.234     0.143          1.000          1.000        1.000


WHAT HELD
---------
4. THE ONE THAT MATTERED. Frozen 0.180 -> lookup 1.000. The entire 0.82 of
   headroom is closed by a single input-dependent operation, on the same
   substrate, with the same readout and the same data. docs/notes/006 §7 is
   confirmed on our own generator rather than inferred by analogy from gated
   convolutions and state-space models.

   Read alongside g0-02: doubling the substrate bought 0.008; adding one lookup
   bought 0.820. Capacity was never the constraint. Content-addressed retrieval
   was, and it is a hundred times the effect.

1. +lookup-token = 1.000, as predicted and by construction.

3. lookup-only = 1.000. The substrate contributes NOTHING once the lookup is
   present. The readout does not need it at all.

5. Survives n_pairs=8: 1.000 against a frozen 0.143. A lookup does not care how
   many pairs there are, which is exactly what distinguishes retrieval from
   storage.


WHAT WAS REFUTED
----------------
2. Predicted +lookup-state at 0.55-0.85, clearly below +lookup-token, on the
   grounds that a substrate state has to be decoded rather than read and is a
   blur of everything present at the time. Measured 1.000 -- identical to the
   token variant.

   THE PREVIOUS SWEEP ALREADY CONTAINED THE ANSWER AND IT WAS NOT USED. g0-02's
   connection control decoded the current token from the substrate state at
   1.000. So the state at the position after a key IS a lossless encoding of the
   value token, for a linear readout. "Decode the state there" and "read the
   token there" were never two different difficulties, and the control had
   already said so.

   This is a prediction that was refutable from evidence already in hand. Worth
   recording as its own kind of error: not an unmeasured assumption, but a
   measured one that was not carried forward. The flagged risk -- that state
   mode might land near CHANCE -- was wrong in the opposite direction.


HOW MUCH THIS IS WORTH, DEFLATED
---------------------------------
A 1.000 here is not impressive and must not be reported as though it were.

On MQAR, "the token following the last occurrence of the current token" IS the
queried value, by the construction of the task. The lookup returns the answer.
The result is close to tautological.

What it genuinely establishes, which is not nothing:

  - The 0.82 headroom is REACHABLE rather than theoretical. g0-02 left this open
    and explicitly warned that unreachable headroom would make every future null
    uninterpretable. It is reachable.
  - The gap is attributable to ONE NAMED OPERATION. Not capacity, not the
    readout, not substrate size, not the task being too hard. One lookup.
  - The remaining question sharpens usefully: "is MQAR learnable" becomes "can
    this lookup be learned". That is a far better question to spend a trained
    model on, and it is a much smaller target than the original.

What it does NOT establish, unchanged from before the run: nothing here learned
anything. The lookup is hand-written. G0 step 3 proper still requires a model
trained from scratch on this generator.
