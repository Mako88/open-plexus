How many slots would it take?
=============================

Script: experiments/g10_05_how_many_slots.py
Status: RUN, at chunk 64 and chunk 256. Counting only -- no model, no training,
        no vectors. Seconds, local.

ANSWER: 8 slots per character recovers 83-97% of the prize, which is inside the
        capacity range the g9 line already works in. But the structure needed is
        PER-KEY and the tag's budget is GLOBAL, so they are not the same
        mechanism -- correcting g10-04, which said they were.


IN PLAIN TERMS
---------------
The previous run said the device loses because it blends everything it has seen
about a letter into one average, where a counter keeps them apart. The obvious
repair is to keep a few of them apart instead of all or one.

So: how few is enough? Eight turns out to be most of the way, and sixteen is
essentially all of it. That is a small number, which is the good news.

The bad news is that it has to be eight *per letter*, not eight in total, and
the thing already built keeps a budget in total.


PREDICTIONS -- REGISTERED BEFORE THE RUN
------------------------------------------
Written into the script before it ran:

    the curve flattens by 4-8 slots  -> the g9 tag's capacity range covers it
                                        and a tiny node can afford it
    it needs dozens                  -> per-character storage is the cost and
                                        this is not a tiny-node mechanism
    unbounded barely beats 1 slot    -> superposition was not the limit and
                                        g10-04 is wrong


THE RESULT
-----------
                      chunk 64              chunk 256
    slots         bits   of prize       bits    of prize
        1        6.221         0%      6.113          0%
        2        6.106        49%      5.893         29%
        4        6.028        83%      5.659         59%
        8        5.995        97%      5.475         83%
       16        5.990        99%      5.381         96%
       32        5.988       100%      5.349        100%

    the whole prize    0.232 bits at chunk 64, 0.765 at chunk 256

**The first prediction holds and the third is refuted.** Unbounded counting beats
a single superposed successor by a wide and growing margin, so superposition is
confirmed as the limit; and the curve flattens early, at 4-8 slots at chunk 64
and 8-16 at chunk 256.

**Slots needed grows with context**, which is what keeping distinct occurrences
predicts: a longer window holds more occurrences of `e` to keep apart. So does
the prize.


THE CORRECTION, AND IT IS TO MY OWN CLAIM ONE CYCLE OLD
---------------------------------------------------------
[g10-04](g10-04-does-context-help-this-model.txt) said a bounded set of distinct
items "is a capacity-bounded set of slots -- **and the g9 line has already built
one**", and called it the first structural connection between the gating work and
goal 2.

**That is too strong.** `tag_slots` is documented as *"how many WRITES the tag
may hold at once"* — one budget for the whole interval. What this measures is 8
slots **per character**, which at a vocabulary of 86 is up to 688 stored
successors rather than 8.

They share an idea — keep a bounded set of distinct things instead of
superposing everything — and they are not the same structure. The connection is
real and it is an analogy, not an implementation that already exists. Corrected
in g10-04.


WHAT IT WOULD COST A TINY NODE, WHICH IS THE PART THAT MATTERS
-----------------------------------------------------------------
If a slot holds a VECTOR, 688 slots at width 32 is 22,016 numbers against a
store of 32x32 = 1,024. **Twenty-one times the store**, which is not a tiny-node
mechanism.

If a slot holds a TOKEN ID, it is 688 integers, and the successor's vector is
regenerated from `(seed, token)` on demand. That is `derived_keys`, the standing
dependency note 024 identified for the whole g9 line, load-bearing again here for
a completely different reason.

**So the cost of this mechanism turns entirely on the same property the gating
line already rests on.** That is worth knowing before it is built, and it is not
a coincidence worth much until someone checks whether the readout can consume
regenerated vectors as cheaply as stored ones.

That check is not done here and is the next question, not this one's answer.


COST

Seconds, local. Counting only.


WHAT THIS IS NOT
-----------------
**A ceiling, not a model.** No readout, no training, no vectors. A real
mechanism reaches some fraction of this, exactly as the tag reaches a fraction
of the oracle in the g9 line. Quoting 5.475 as what a slot-based memory would
score on this corpus would be the same error g10-03 made: a number measured on
one thing applied to another.
