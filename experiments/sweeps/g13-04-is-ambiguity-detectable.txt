Can the model tell, before searching, whether searching would help?
===================================================================

Script: experiments/g13_04_is_ambiguity_detectable.py
Status: DISPATCHED. Predictions registered before the matrix ran.

ANSWER: pending. A smoke seed is recorded below.


IN PLAIN TERMS
---------------
The model can answer a question by trying several possibilities and checking
which one works out. That helps when the question really is ambiguous and hurts
when it is not -- trying alternatives to something already correct can only
replace a right answer with a lucky-looking wrong one.

So it should only try when trying is worth it. This asks whether the model can
tell those two situations apart using something it can actually see, rather than
being told.


WHY THIS EXISTS
----------------
g13-03 measured search doing precisely what it was built for and damaging the
case it was not:

    search4 - walk at out-degree 1       -0.054
    search4 - walk at out-degree >= 2    +0.092

The test set is about half of each, so they cancel and the overall gain is
+0.008, inside 2 SE. **The tie is not evidence against search. It is evidence
that search should not run unconditionally.**

A gate keeps the +0.092 and gives back the -0.054 -- if the model can tell the
cases apart before committing to the walks.


THE CANDIDATE, AND WHY IT MIGHT NOT BE ANOTHER DEAD END
--------------------------------------------------------
`search.decode_margin` is the gap between the top two candidates of the first
decode: `key(FACT, S)` read from the store and scored against every token's
value vector.

**Decision 93 is the bar and the warning.** It measured norm, entropy, peak, gap
and kurtosis of a retrieval, and the best linear separator over all five --
FITTED WITH THE LABELS -- reached **0.628** against 0.500 for guessing. Every one
of those asks "does this retrieval feel reliable".

The margin asks something structural instead: when ONE relation is bound to a
key the decode is peaked, and when SEVERAL are they compete. It reads the
superposition rather than guessing at it.

That is an argument, and this project's record on arguments is poor. Hence a
measurement first.


WHAT IS MEASURED
-----------------
**Accuracy is not measured here at all.** Each test sequence is run with a
`trace`, the entry at the answer position is read, and its
`search_decode_margin` is scored against the queried subject's true out-degree
-- task metadata a running system CANNOT see. The out-degree is the LABEL; the
margin is the proxy.

Reported as AUC: the probability a random out-degree-1 sequence shows a wider
margin than a random out-degree-2+ one. 0.500 is chance, ties count as half.

`search_endpoint_margin` -- the gap between the best and second-best walk -- is
recorded alongside as the rival. It is better informed and costs the walks, so a
gate using it has already paid; if it is not clearly better, the cheap signal
wins on cost alone.

The trace is the documented channel for exactly this question: *"one dict
appended per step carrying the signals a gate could actually consult"*.
Observation only, and `test_trace_observes.py` pins that a traced run and an
untraced one agree.


PREDICTIONS
-----------
  P1  THE DECISION. Decode margin AUC > 0.75, well clear of decision 93's 0.628.
      Below 0.75 the gate is not worth building on this signal.

  P2  Median margin at out-degree 1 is more than twice the median at 2+. Medians
      rather than means so one badly-behaved sequence cannot carry it.

  P3  The endpoint margin does NOT beat the decode margin by more than 0.05 AUC.
      Refuted would mean the expensive signal earns its cost and the gate should
      be built the other way round -- search first, then decide whether to trust
      the result.

  P4  Separation holds at every width. A width artefact is not a mechanism.

  P5  AUC stays below 0.95. The margin is a proxy for a property it cannot fully
      observe, and a near-perfect score would suggest the label is leaking into
      the measurement rather than being predicted.


THE SMOKE SEED, RUN BEFORE DISPATCH
------------------------------------
Width 256, seed 0, 200 test sequences:

    out-degree 1    n=120   mean 0.7714   median 0.7786
    out-degree 2+   n=80    mean 0.2779   median 0.1083
    AUC                                            0.879

Well clear of 0.628, and the medians differ by 7x. One seed, one width; the
matrix runs eight seeds at three widths.


COST
----
3 widths x 8 seeds = 24 cells, in 8 jobs of 3.

Estimated from the MOST EXPENSIVE cell (width 256), measured by `--cost`:

    21.5 ms per training sequence
    0.6 min to train one cell (400 x 4)
    ~2 min per job

Each cell trains one model and then runs inference with a trace; there are no
sweep arms, which is why this is cheaper than g13-03 at the same widths.


MEASURED ON
-----------
openplexus/tasks/kinship.py, hops 2, 12 people, 10 facts, width 64/128/256,
`search_branches=4` so the decode has four candidates to rank.
