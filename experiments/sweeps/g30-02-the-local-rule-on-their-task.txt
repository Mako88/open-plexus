The local contrastive rule on FB15k-237's own task
===================================================

Script: experiments/g30_02_contrastive_link_prediction.py  (to be written)
Status: NOT RUN. Predictions registered and committed before the script exists.

ANSWER: pending.


IN PLAIN TERMS
---------------
`g30-01` read the raw store on FB15k-237's own metric and it lost to counting by a
factor of 28. That was the STORE -- outer products of random vectors, nothing
learned. It says nothing about whether this project's learning rule can do the job,
because the learning rule was not in the run.

This puts it in. The rule is the one `g23-04` used to beat counting on eighteen
graphs: **pull the right answer closer, push every wrong answer away, one example at
a time, using only what one machine can see.** No global gradient, no barrier, no
second pass over the data.

**The question is whether a rule that never synchronises reaches a number the
outside world would recognise.** That is the project's whole premise on somebody
else's benchmark, with an opponent -- counting -- that is computed here rather than
quoted.


WHY THIS EXISTS, AND WHAT IT IS NOT
------------------------------------
`g30-01` deferred it in writing: *"a contrastive arm on this metric is a separate
run and is not being quoted from this one."* This is that run.

**This is not a novel scoring function and will not be described as one.** Scoring a
triple by `<h * r, t>` -- elementwise product, then inner product -- is a standard
knowledge-graph scoring form and predates this project by years. Rule 1 forbids
letting a recalled name gate a claim, so no published system is named or quoted
here; what matters is that **the scoring form is ordinary and the UPDATE is the
variable**.

So the comparison this run is built for is not "our model against theirs". It is:

    the same scoring form, learned by a LOCAL per-example rule with no barrier,
    against a baseline that needs no learning at all

If the local rule cannot beat counting on this data, that is a fact about the rule
and it is on-goal to find it.


THE MECHANISM, AND THE ONE DEVIATION
-------------------------------------
`tools/relation_contrastive.learn` already implements the rule. Two changes, both
parameters rather than a fork, because rule 9 says one implementation per behaviour:

  TWO TABLES  entities and relations are different alphabets here, where CLUTRR
              composes relations with relations. `learn` gains a second table; when
              it is absent the existing single-table behaviour is unchanged, byte
              for byte, and the existing tests still pin it.

  SAMPLED     the current rule contrasts against EVERY other symbol, which its own
  NEGATIVES   docstring calls a virtue: *"no negative sampling schedule has to be
              chosen and none can be got wrong."* **That virtue does not survive
              14,505 entities** -- a full contrast is a 14,505-row outer product per
              example, 272,115 times per epoch. So negatives are sampled.

**The deviation is named because it is a real weakening.** A sampled contrast is a
schedule, the schedule can be wrong, and `K` is now a knob nobody has tuned. It is
swept rather than picked, and the full-contrast path stays as the default so no
CLUTRR or graph result moves.


THE MEASUREMENT
---------------
Identical protocol to `g30-01`, reusing its code rather than restating it: filtered
tail-side link prediction, MRR and Hits@1/3/10, unfiltered always printed beside it,
store and embeddings built from TRAIN only, unanswerable test triples counted rather
than dropped.

Arms, all on the same test set on the same machine:

    contrastive     the local rule, widths and K swept
    untrained       the SAME code with epochs 0 -- the gate
    frequency       g30-01's opponent, recomputed not carried
    raw store       g30-01's 0.0122 / 0.0232, quoted because it is the same
                    protocol in the same file family
    chance          1/14,505


PREDICTIONS
-----------
  P1  THE GATE, and it is two conditions. The untrained arm scores near chance
      (under 0.001), and the trained arm beats the raw store's 0.0232.

      If untrained scores well the evaluation is measuring something other than the
      representation and nothing else in the run is reportable -- the same gate
      `relation_contrastive` already carries for CLUTRR. If trained does not beat a
      store of random outer products, the objective is doing nothing.

  P2  THE TEST. Filtered MRR exceeds 0.10, which is more than 4x the raw store.

      Registered as a number rather than as "improves", because "improves" is
      satisfied by 0.024 -> 0.025.

  P3  It still LOSES to `frequency`'s 0.3378.

      **I expect to lose, and by a factor between 1.3x and 3x.** Counting exploits
      the fact that many FB15k-237 relations have one dominant tail, which no
      representation has to learn because it is not a pattern. Beating it outright
      would be a bigger result than anything this project has produced and should be
      checked for a leak before it is believed.

  P4  THE ONE I AM LEAST SURE OF. More negatives help and then stop -- the best `K`
      is interior to the swept set, not at either edge.

      `g4-01`'s calibration is that a grid whose arms pin at the edges has not swept.
      Checked with `tools/grid.py` rather than by reading the column.

  P5  Widening helps SUBLINEARLY, as it did for the raw store, which moved 1.90x for
      a doubling.

      If the learned arm scales BETTER than the raw store with width, that is the
      first evidence the objective changes how capacity is used rather than just
      what is written into it.


WHAT WOULD MAKE THIS NOT COUNT
--------------------------------
**Test or valid triples reaching the embeddings.** Training is TRAIN only. The
filter reads all three splits, which is the convention and is not the same thing --
`g30-01` states this and the code is shared, so it cannot drift between the two runs.

**The untrained arm not actually being untrained.** It is the same call with epochs
0, so a bug in the learner cannot make the gate pass by accident.

**Tuning one arm.** `frequency` has nothing to tune, which sounds like it settles the
issue and does not: the hazard here is tuning OURS until it wins and reporting the
best cell. The sweep reports the full grid, and the headline is the best cell with
the grid printed beside it so the reader can see how much searching bought.

**Quoting a published number.** None is quoted. Setting this beside the literature
requires reading the literature, which is a separate job that starts with reading.


COST
----
Sampled negatives put an epoch at roughly two minutes at width 128 -- 272,115
updates of a few small matrix operations each. Ranking is 20,438 x 14,505, batched.
Estimated minutes per cell, and **estimated is the word**: the local-to-runner factor
is 8x measured, so a grid goes to Actions rather than to this machine if a cell
exceeds the ten-minute line `g8_05` earned.
