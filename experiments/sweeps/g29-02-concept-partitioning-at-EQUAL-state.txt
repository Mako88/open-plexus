Concept partitioning at equal state, because g29-01 was not
============================================================

Script: experiments/g5_01_scaling.py --mode concept, at reduced width
Status: RUN, 10 of 10 cells. Predictions committed at `cfbbdb3` before dispatch.

ANSWER: **P1 and P2 HELD, at a QUARTER of the state rather than the 0.60x this
        file predicted. P3 REFUTED -- the cell is still a ceiling.**

    concept     1.0000  in 30 cells of 30, spread over learning rates 0.0000
    dimension   0.7549  mean, range 0.685-0.808, spread 0.1229

So concept partitioning solves `g5-01`'s cell using **a quarter of the numbers and
a quarter of the machines**, where dimension partitioning reaches 0.755. That
cannot be bought with state, which is what `g29-01` could not say.


THE STATE FIGURES IN THIS FILE WERE WRONG, AND THE CORRECTION FAVOURS US
--------------------------------------------------------------------------
This file predicted the concept arm would hold **88,128** numbers at 16 nodes,
0.60x the dimension arm. It actually held **37,440** at **4** nodes, 0.25x.

`g5_01_scaling.py` derives the machine count from the width -- `groups = width //
MACHINE_WIDTH`, `MACHINE_WIDTH = 16` -- so asking for width 64 also asked for four
machines rather than sixteen. **That line was not read before the number was
written down.** Verified from the artifacts' own `partitions` field, which reports
4 for the concept arm and 16 for the dimension arm.

    arrangement                         width  machines     numbers   vs dimension
    dimension, as g5-01 runs it           256        16     147,520          1.00x
    concept,   AS ACTUALLY RUN             64         4      37,440          0.25x
    concept,   as this file predicted      64        16      88,128          0.60x
    concept,   g29-01's confounded arm    256        16   1,132,608          7.68x

**Third time in one session that a number reached a record without being read off
the run.** The pattern each time is a figure derived by reasoning about a
parameter rather than by looking at what the parameter did, and each time rule
11b's *"only the data says what happened"* is what caught it.


AND g5-01's GRID TIES MACHINE COUNT TO WIDTH, WHICH IS WORTH RECORDING SEPARATELY
-----------------------------------------------------------------------------------
`WIDTHS = (16, 32, 64, 128, 256)` with `P = width // 16` gives `P = (1, 2, 4, 8,
16)`. So the sweep whose exponent is `#10`'s headline **never varies width at a
fixed machine count** -- it moves along a diagonal where both grow together, and
its width-16 cell is not partitioned at all.

That is not a defect in `g29-02`, which inherits the design deliberately so the
arms stay comparable. It is a fact about what `g5-01`'s 0.69 exponent is an
exponent OF, and it has not been written down before.

    width   machines   dimension state   concept state
       16          1            5,440           5,568
       32          2           11,328          12,608
       64          4           24,640          37,440
      128          8           57,408         173,120
      256         16          147,520       1,132,608

At EQUAL width the concept arrangement costs more, from 1.02x at width 16 to 7.68x
at width 256, because each node carries a full-width store. That is the price of
the arrangement and it is why `g29-02` had to drop the width to make the
comparison fair.


SCORECARD
---------
  P1  HELD. Concept solves the cell, 1.0000 against the 0.95 bar, at 0.25x state
      rather than the 0.60x predicted -- a harder test than the one registered.

  P2  HELD. 1.0000 against dimension's 0.755, at lower state and fewer machines.

  P3  REFUTED, and this is the one that matters for what comes next. The concept
      arm's spread across five learning rates is **0.0000** -- identical to
      `g29-01`. Dropping the width from 256 to 64 did not move it off the ceiling.

      A grid where every cell is perfect cannot rank anything and cannot fit a
      slope. **So `#10` is not answered.** What is established is that the wall
      `g5-01` measured is a property of DIMENSION splitting; concept partitioning's
      own wall is further out and has never been looked for.

  P4  HELD, and by more than expected. Concept cells took **8-22 minutes** against
      `g29-01`'s 47-53 at width 256; dimension cells took 24-31. So the
      arrangement is not intrinsically 1.7x more expensive -- that was width 256
      carrying sixteen full stores. At four nodes and width 64 it is CHEAPER than
      the dimension arm it beats.


WHAT THIS DOES NOT SETTLE
--------------------------
**The exponent.** One sequence length cannot fit a slope, and both arms would need
to be swept over length before `0.69` has a counterpart.

**Whether concept scales.** Its state grows as `machines x width^2` where dimension
grows as `width^2`, so the arrangement that wins here is the one that gets more
expensive faster. At width 256 it is already 7.68x. **Whichever wall concept has,
the cost table above says it will be paid for in memory per machine** -- which is
exactly the quantity `#10` is about.

**Anything about longer sequences.** `g29-03` pushes `seq_len` until the concept arm
stops solving, which is the only way to find the number this line of work needs.


IN PLAIN TERMS
---------------
The last run looked like the best news this project has had: splitting the work
by CONCEPT scored a perfect 1.0000 on the exact problem where splitting it by
DIMENSION stalls at 0.77.

It was not a fair fight. The concept arrangement gives every machine a full-size
memory of its own, so sixteen machines hold sixteen memories. The dimension
arrangement holds one and slices it. Measured, on the actual objects:

    dimension, 16 groups at width 256      147,520 numbers
    concept,  16 nodes  at width 256     1,132,608 numbers

**Seven and a half times the memory.** A win under that is not evidence about the
arrangement; it is evidence that more memory helps, which nobody doubted.

This re-runs the same cell with the concept arrangement given LESS memory than its
opponent, so a win cannot be bought with state.


WHY THIS EXISTS, AND IT IS NOT A NEW INSIGHT
----------------------------------------------
**The confound was already written down, twice, in this repository, before
`g29-01` was dispatched.**

`local_memory.py` says it at the definition of the knob: each node keeps a full
`d x d` store, the comparison at equal `d_model` is *"biased TOWARD partitioning,
which is deliberate"*, a LOSS would be unambiguous, and **a win "would need the
g10-09 equal-state treatment before it meant anything."**

`tests/test_concept_routing.py` says it again in its own docstring: *"the apparent
gain is the extra state, not the arrangement"*, with the numbers -- 16 nodes of
width 32 score 0.988 while a monolithic store holding the same count scores 1.000
-- and names `g10-09` as the retraction that established it.

`g29-01`'s own WHAT WOULD MAKE THIS NOT COUNT section lists carried knobs and
cross-sweep quoting. It does not list this. **Neither document was read before
dispatch**, which is rule 19's failure -- not knowing what exists -- applied to a
warning rather than to code.

**So this file is the correction, and the calibration is that a `not count`
section written from memory misses what the source already knew.** The cheap habit:
before dispatching a sweep on a knob, read the knob's own definition and its test's
docstring, because a confound recorded there is a confound somebody already paid
for.


THE MEASUREMENT
---------------
`g5-01`'s cell, unchanged: `seq_len 384`, 16 groups, learning rates
{0.01, 0.02, 0.05, 0.1, 0.2}, three seeds, sixteen epochs. The dimension arm stays
at width 256 and is re-run rather than quoted, as in `g29-01`.

The concept arm runs at **width 64**, which holds **88,128** numbers against the
dimension arm's 147,520 -- **0.60x, deliberately disadvantaged.** Matching exactly
would need width ~85 and a width the grid has never used; being under is the
stronger test and needs no interpolation.

    arm                       width   state    state vs dimension
    dimension, 16 groups        256   147,520            1.00x
    concept,   16 nodes          64    88,128            0.60x
    concept,   16 nodes         256 1,132,608            7.68x   (g29-01, confounded)


PREDICTIONS
-----------
  P1  THE TEST. The concept arm at width 64 still SOLVES this cell -- pooled above
      0.95 at its best learning rate.

      **I am genuinely unsure and would put it near even.** If it holds, concept
      partitioning beats dimension partitioning while carrying 40% less state, the
      confound is dead, and `#10`'s verdict reopens on the arrangement the project
      actually intends to use. If it fails, `g29-01` measured seven times the memory
      and nothing else.

  P2  Whatever it scores, it BEATS the dimension arm's 0.755 at equal or lower
      state.

      Weaker than P1 and the one that matters for the wall: the claim is not that
      concept is perfect, it is that per-machine full width buys more than the same
      numbers sliced. Refuted if it lands at or below 0.755.

  P3  THE CEILING PROBLEM, registered because `g29-01` hit it and did not say so.
      At width 64 the concept arm is NOT saturated -- its five learning rates do
      not all return the identical score.

      `g29-01`'s concept arm returned 1.0000 in **thirty cells out of thirty**, zero
      variance across seeds and learning rates. A grid where every cell is at the
      ceiling cannot rank anything, so `g29-01` could not have detected a learning
      rate effect had one existed. If width 64 also saturates, this cell is still
      the wrong instrument and the next run must go to longer sequences.

  P4  THE ONE I EXPECT TO BE WRONG. The concept arm at width 64 costs LESS runner
      time per cell than at width 256.

      `g29-01`'s concept cells took 47-53 minutes against the dimension cells' 26-30,
      so the arrangement costs about 1.7x at equal width. Registered because cost is
      a property of the arrangement that the project will have to live with, and
      nobody has written down how it scales.


WHAT WOULD MAKE THIS NOT COUNT
--------------------------------
**State counted by hand rather than measured.** The three figures above come from
walking the live object graph of a model that has actually run a 384-token
sequence, because `ConceptStore` allocates nodes lazily and a freshly constructed
model reports 81,984 for all three arrangements. A count taken at construction time
would have shown no difference at all and confirmed the confound did not exist.

**Quoting `g29-01`'s concept number.** It stands only as *"routing does not break
learning at 7.7x state"*, which is what `tests/test_concept_routing.py` already
established at one seed. It is not evidence about the wall and is not quoted as any.

**A different `alone`.** `g5-01`'s `alone` is one width slice's score; under concept
it is one node's FACTS and the script returns `nan` rather than a comparable number.
The fitted quantity is POOLED in both arms.

**Reading this cell as the exponent.** It is one sequence length. `#10` is about how
the required width GROWS with length, and one cell cannot fit a slope. This decides
whether the exponent is worth measuring, which is what `g29-01` was for and what it
did not deliver.
