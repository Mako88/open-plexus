G4 — does the traffic fit a home connection?
============================================

Script: experiments/g4_03_bandwidth.py
Status: RUN, twice. **G4 PASSES** -- but not via the escape it was built to
        test. Predictions 3, 4 and 6 all chased "speak less often" and all
        three were refuted; it did not matter, because a TOKEN vote is 12
        bytes at any vocabulary against 400,008 for a distribution, so a
        node can speak every step and use a thousandth of a home uplink.
        Voting is free at eight nodes (0.658 against 0.658). ONE SEED.

        Previously: **Prediction 3 REFUTED, and badly.** Silence is not graceful:
        halving the speaking rate costs 0.31 agreement immediately. 1 and 2
        held. The refutation identifies the fix, and the fix is a protocol
        change rather than a tuning: a node with its own complete readout
        sends a TOKEN, not a distribution.


WHAT G4 ASKS
------------
"Does the required cross-machine traffic fit consumer broadband? Refuted if the
traffic needed for the margin exceeds what a home connection carries."

Two directions, and only one of them has ever been accounted for.

**Inbound is settled and cheap.** `Network.bytes_per_step_inbound` returns
`header + 4`: a node receives a token id and nothing else, at any width, because
[note 012](../../docs/notes/012-broadcast-the-token.md) established that a node
can derive any key it needs from `(seed, token)`. Four bytes per step per node is
not a bandwidth problem on any connection.

**Outbound is not accounted for anywhere, and it is the expensive one.** A node
replies with a complete vote: `vocab_size` float64s.

    vocab     41  ->     328 bytes per node per step        MQAR
    vocab  1,000  ->   8,000 bytes
    vocab 50,000  -> 400,000 bytes per node per step        real language

At 400 KB per node per step, **one node at ten steps per second saturates a home
uplink on its own.** If every node must vote every step, G4 fails at any
realistic vocabulary and it fails by three orders of magnitude, not by a margin
that tuning closes.

**But voting may not be required.**
[g4-01](g4-01-no-global-readout.txt) removed the global readout and found a
single machine's answer stands alone — 0.949 at eight-way, 0.996 at four-way —
so pooling is *optional rather than required*, which is the claim C1 actually
needs. If a node need not speak every step, the outbound cost is not
`vocab x rate x nodes`; it is whatever the speaking rate turns out to be.

**So G4 is not "how big is a vote". It is "how often must a node speak, and what
does accuracy cost when it speaks less".** That is the sweep.


WHAT GETS MEASURED
-------------------
1. **Outbound bytes per node per step**, counted in the container testbed rather
   than computed. The testbed sends real packets, so this is an observation and
   not arithmetic dressed up as one.
2. **Accuracy against speaking rate.** A node votes on a fraction `p` of steps
   and stays silent otherwise; the driver sums whatever arrives. `p = 1` is
   today's behaviour.
3. **The same, against vocabulary size**, since the cost per vote scales with it
   and the accuracy cost of silence may not.


PREDICTIONS -- written before any measurement
-----------------------------------------------
1. **Inbound is trivially within budget at every configuration.** Four bytes per
   step per node, and it is a broadcast, so it is the same four bytes however
   many nodes there are. Stated because it is the half already argued and it
   should be confirmed rather than assumed.

2. **Outbound at `p = 1` fails G4 for any vocabulary above a few thousand.** This
   is arithmetic and I expect it to hold exactly. Reporting it as a finding would
   be reporting a multiplication, so the sweep's job is the next prediction.

3. **Accuracy degrades gracefully as `p` falls, and much more slowly than
   linearly.** g4-01 found one machine of eight already scores 0.949 alone, so
   the pooled answer is heavily redundant. Guess: `p = 0.1` costs under 0.05
   accuracy at eight nodes. **If this holds, G4 passes** — a tenth of the votes
   is a tenth of the bytes.

4. **The tolerable `p` falls as node count rises.** More nodes means each
   contributes less, so silence from any one matters less — but the driver needs
   *some* votes per step, and with many nodes each voting rarely, a step may
   receive none at all. Guess: there is a floor around a handful of votes per
   step regardless of how many nodes exist, which would make outbound traffic
   scale with **steps**, not with **nodes**. That would be the strongest possible
   G4 result and it is the one I would most like to be true, so it gets the most
   scrutiny.

Most likely wrong: (4). It is the favourable direction and it is the one where
wanting the answer could shape the measurement.


WHAT WOULD REFUTE WHAT
-----------------------
- p=0.1 costs little, floor exists    -> G4 PASSES, and outbound scales with
                                         steps rather than nodes
- p=0.1 costs a lot                   -> pooling is not as optional as g4-01
                                         implied, and G4 fails at language scale
- no floor; votes needed per node     -> traffic scales with nodes and the
                                         tiny-node story has a bandwidth wall
                                         underneath its accuracy wall
- inbound is not 4 bytes              -> note 012 is wrong about what crosses the
                                         wire, which would be a bigger finding
                                         than G4


WHAT THIS CANNOT SETTLE
------------------------
**Training traffic.** Everything here is inference. The delta rule learns from a
target at every scored position, and how *that* is distributed has never been
designed, let alone measured. G4 as written asks about running, not learning, and
the ladder does not currently have a gate for the second.

**Real network conditions on the byte counts.** The testbed measures on a Docker
bridge. Retransmission under loss changes bytes on the wire, and the 2% loss
figure used in note 014 is a guess at a bad link rather than a measurement of
one.


RESULT
------
Agreement with the whole network's answer, by speaking rate. 1.000 means the
silence changed nothing.

 nodes       1.0       0.5      0.25     0.125       0.0
     2     1.000     0.692     0.692     0.692     0.692
     4     1.000     0.692     0.375     0.375     0.375
     8     1.000     0.692     0.375     0.258     0.258
    16     1.000     0.692     0.375     0.258     0.067

Cost per node per step:

  listening            9 bytes   independent of vocabulary
  one vote           336 bytes   at vocab 41
  one vote         8,008 bytes   at vocab 1,000
  one vote       400,008 bytes   at vocab 50,000

Steps per second a 10 Mbit/s uplink supports, for ONE speaking node:

  vocab      41        3,720 steps/s
  vocab   1,000          156 steps/s
  vocab  50,000            3 steps/s


THE PREDICTIONS
----------------
1. **Inbound is trivially within budget -- HELD.** Nine bytes per step per node,
   independent of width, vocabulary and node count, because it is a broadcast of
   a token id and a flag.

2. **Outbound at p=1 fails for any real vocabulary -- HELD**, and it is
   arithmetic. Three steps per second at vocab 50,000 is not a margin that tuning
   closes.

3. **Accuracy degrades gracefully as p falls -- REFUTED, emphatically.** The
   guess was that p=0.1 would cost under 0.05 at eight nodes. Measured: p=0.125
   at eight nodes gives **0.258** agreement, so three quarters of the answers
   changed. Halving the rate costs 0.31 at every node count.

4. **A floor of a few votes per step -- REFUTED with it.** There is no floor;
   at 16 nodes speaking once per step, agreement is 0.067. Fewer speakers is
   simply a worse answer, not a noisier one.

**Both refuted predictions were the favourable direction, and I named (4) in
advance as the one where wanting the answer could shape the measurement.** It did
not survive contact, and neither did (3).


WHY, AND I MISREAD g4-01 TO GET HERE
--------------------------------------
The predictions rested on "pooling is optional -- one machine of eight scores
0.949 alone". That is g4-01's finding and it is true, **but it is about a
different architecture than the one being measured here.**

g4-01 gave each machine its **own complete readout**, so its answer is a whole
answer. The distributed driver does something else: each node returns a partial
contribution and the driver SUMS them, so the sum over every node reconstructs
the full matrix product. Dropping half the terms of a sum does not give a noisier
estimate of the same quantity -- **it gives a different quantity**, and there is
no reason for its argmax to match.

So silence is not sampling. It is amputation.


WHAT THIS ACTUALLY SETTLES, WHICH IS MORE THAN A GATE
-------------------------------------------------------
**G4 fails as the system is currently built**, at any realistic vocabulary, and
the speaking-rate escape does not exist. But the refutation names the fix
precisely, and it is one this project has already validated.

If each node carries its own complete readout -- which `partitions` implements
and g4-01 measured as costing nothing at adequate width, 1.000 against 1.000 --
then a node's answer is a whole answer. And a whole answer is a **token id**, not
a distribution over the vocabulary.

    today, per speaking node per step:   8 + 8 * vocab bytes
    with a complete readout:             4 bytes

**That is a factor of a hundred thousand at vocab 50,000**, and it removes the
vocabulary from the bandwidth equation entirely -- the same move note 012 made
for the inbound direction, applied to the outbound one.

It also changes what pooling means. Summing partial contributions requires
everyone; combining whole answers is a vote, and a vote tolerates absence by
construction. That is what C3 wants and what the current protocol cannot give.

**Not built, not measured.** The claim above is arithmetic plus g4-01's accuracy
figure, and the accuracy of a token-vote network at low speaking rates is a
different measurement that has not been made. G4 stays open, with a named
candidate rather than an open question.


THE FIX, BUILT -- PREDICTIONS BEFORE MEASURING
================================================
`combine="vote"` is implemented. A node sends `argmax` of its own score vector --
four bytes plus a step index -- and the driver tallies. Summing remains the
default, because it is bit-identical to the single-process model and voting is an
approximation by construction.

Predictions, written after the code and **before any number from it**:

5. **Voting costs accuracy at full speaking rate.** Summing reconstructs the
   exact product; voting throws away everything except each node's argmax. g4-01
   put a lone eight-way machine at 0.949, so a plurality of eight such opinions
   should be better than one and worse than the exact sum. Guess: agreement
   0.85-0.98 at `p = 1`, eight nodes.

6. **Voting degrades far more gracefully than summing.** This is the whole point.
   Summing lost 0.31 when half the nodes went quiet, because a partial sum is a
   different quantity. A vote missing half its voters is the same kind of thing
   with fewer voters. Guess: at `p = 0.5`, voting loses under 0.10 where summing
   lost 0.31.

7. **More nodes helps voting and does not help summing.** Sixteen opinions
   outvote noise better than four. Under summing, node count was irrelevant to
   the damage -- every rate cost the same 0.692/0.375/0.258 regardless. If
   voting shows the same flatness, the tally is not doing what a tally should.

8. **Outbound drops to 12 bytes per speaking node per step**, independent of
   vocabulary. Arithmetic, stated so the sweep confirms rather than assumes it.

Most likely wrong: (6), and it is the favourable direction again -- the same
place predictions 3 and 4 died. The specific way it could fail: if the nodes'
argmaxes are highly correlated, a vote carries little more information than one
node, and losing voters costs as much as losing terms. That would mean the
partition is not producing independent opinions, which is a finding about the
decomposition rather than about the protocol.


THE FIX, MEASURED -- G4 PASSES, AND NOT FOR THE REASON PREDICTED
=================================================================
Two invalid attempts preceded this one and both are recorded above and in
experiments/g4_04_token_votes.py. The valid measurement trains with
`partitions = nodes`, so each node's readout has learned to answer alone, and
refuses to report anything if the single-process reference is at or below the
trivial floor.

Accuracy, seq_len 192, width 128, one seed. Trivial floor 0.344.

    nodes  one process      1.0      0.5     0.25    0.125     combine
        2        0.892    0.854    0.892    0.892    0.892     vote
        4        0.754    0.700    0.571    0.675    0.675     vote
        8        0.658    0.658    0.542    0.317    0.433     vote

        2                 0.892    0.892    0.892    0.892     sum
        4                 0.754    0.733    0.675    0.675     sum
        8                 0.658    0.617    0.579    0.433     sum

5. **Voting costs accuracy at full speaking rate -- HELD, and less than
   guessed.** 0.854 against 0.892 at two nodes and 0.700 against 0.754 at four,
   so about 0.04-0.05. **At eight nodes it costs nothing at all: 0.658 against
   0.658.** The guess was 0.85-0.98 agreement; the cost is real at small node
   counts and vanishes at eight.

6. **Voting degrades more gracefully than summing -- REFUTED.** It does not. At
   eight nodes and half rate, summing gives 0.617 and voting 0.542; at quarter
   rate, 0.579 against 0.317. **Summing is the more graceful of the two**, which
   is the opposite of the argument that motivated building the vote at all.

   Named in advance as most likely wrong, and as the favourable direction. Three
   predictions in this file have now died in that direction.

7. **More nodes helps voting -- REFUTED.** Accuracy falls with node count, 0.854
   to 0.658. It falls for the single-process model too (0.892 to 0.658), because
   more partitions means narrower groups, so relative to the reference voting is
   roughly flat rather than improving. More voters does not buy accuracy here.

8. **Outbound drops to 12 bytes per speaking node per step -- HELD**, at any
   vocabulary.

WHY G4 PASSES ANYWAY
----------------------
**The bandwidth problem was the SIZE of a vote, not its frequency.**

    a distribution, vocab 50,000    400,008 bytes    3 steps/s on 10 Mbit/s
    a token, any vocabulary              12 bytes    ~104,000 steps/s

Predictions 3, 4 and 6 all chased the same escape -- speak less often -- and all
three were refuted. It did not matter: **at twelve bytes a node can speak every
single step and still use a thousandth of a home uplink.** The question the sweep
was built around turned out not to need answering.

That is the result, and it is worth separating from the reasoning that reached
it. The reasoning was wrong three times. The arithmetic that ended up mattering
was the one prediction nobody had to test.

WHAT IS STILL OWED
--------------------
**One seed, and the numbers are visibly noisy** -- 0.317 at quarter rate against
0.433 at eighth rate is not a monotone curve, and nothing here has error bars.
The headline (voting is free at eight nodes, 12 bytes at any vocabulary) rests on
a single run and should be repeated before it goes into GOALS.

**Training traffic is still unmeasured**, and the ladder still has no gate for
it. Everything here is inference.

**The accuracy cost at small node counts is real** -- 0.04 to 0.05 at two and
four nodes -- and unexplained. It vanishing at eight is the sort of
non-monotonicity that usually means something else is moving.
