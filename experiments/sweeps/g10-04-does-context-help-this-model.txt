Can this model USE a longer memory, or only be given one?
==========================================================

Script: experiments/g10_04_does_context_help_this_model.py
Status: RUN. Width 32, cap 5.0, one seed, four chunk lengths. Local, minutes.

ANSWER: it captures 24% of what extra context is worth, and the shortfall GROWS.
        Persistence is not the fix, and g10-03's ordering of what to build --
        which I wrote one cycle earlier -- is backwards.


IN PLAIN TERMS
---------------
The previous run found the device's biggest disadvantage was that it forgets
between windows, and recommended building something that remembers across them.

But a gap you cannot close is not an opportunity. So this hands the device longer
and longer windows and watches whether it actually does anything with them. A
counter, given the same windows, improves steadily. The device barely moves.

Giving it a longer memory would hand it more of exactly what it is already
failing to use.


PREDICTIONS -- A DECISION RULE, REGISTERED BEFORE THE RUN
----------------------------------------------------------
Written into the script's docstring before it was executed, because this run
exists to check a recommendation I had already published and reading the numbers
kindly was the whole risk:

    model tracks counting as chunk grows   -> persistence IS the fix, g10-03's
                                              recommendation stands
    model flattens while counting climbs   -> persistence is NOT the fix, and
                                              g10-03's ordering is backwards

Threshold: 60% of counting's gain. Chosen before the run, and generous on
purpose -- a mechanism capturing more than half of what context is worth would
be worth building persistence for.


THE RESULT
-----------
    chunk     model   counting       gap   model accuracy
       64     5.927      5.988    -0.062            0.160
      128     5.804      5.711    +0.094            0.167
      256     5.856      5.349    +0.507            0.182
      512     5.687      4.976    +0.711            0.143

    from chunk 64 to 512:  model gained 0.240 bits, counting gained 1.012
    the model captured 24% of what the extra context was worth

**The gap widens monotonically** — the model starts ahead of counting at chunk 64
and falls a further 0.77 bits behind by chunk 512. Its own curve is nearly flat:
5.927, 5.804, 5.856, 5.687 across an eightfold increase in context.

24% is not nothing, and it is far below the 60% registered in advance.


WHAT IT CORRECTS
-----------------
[g10-03](g10-03-what-is-the-ceiling.txt) listed what to build in this order:

    1. a store that persists across chunks   (worth "up to 2.3 bits")
    2. something that keeps a distribution rather than an average

**That ordering is wrong and it is corrected there.** The 2.3 bits was the size
of the gap a COUNTER would close, and this mechanism closes a quarter of it. The
recommendation rested on the size of a gap rather than on the ability to close
it, which is exactly the error the g9 line has been catching in other forms all
session: a number measured on one thing, applied to another.

The corrected order puts superposition first, and the reason is on this page —
the model's shortfall against counting GROWS with context, which is what
collapsing many occurrences of `e` into one averaged vector predicts.


WHAT THIS POINTS AT, AND IT IS ALREADY BUILT
----------------------------------------------
Something that keeps a bounded set of DISTINCT items rather than one superposed
average is a capacity-bounded set of slots. **The g9 gating line has already
built one** — `tag_slots`, with a fade — for an entirely unrelated reason: to
decide which writes survive a reward.

Two lines arriving at the same mechanism from opposite directions is worth more
than either arriving alone, and it is the first structural connection between the
gating work and goal 2.

**Not a claim that it will work.** The tag was built to select writes, not to
represent a distribution, and the corpus task has no reward signal at all. What
this says is where to look, not what will be found.


WHAT WOULD REFUTE WHAT
-----------------------
- model captures >60% of the gain   -> persistence is the fix. NOT OBSERVED: 24%
- the gap NARROWS with context      -> superposition is not binding. NOT
                                       OBSERVED: it widens at every step
- the model's own curve is flat     -> OBSERVED, 0.24 bits over eightfold context


COST
-----
Four cells, local, minutes, one seed. **One seed is the real limit here** — the
per-chunk numbers wobble (5.856 at chunk 256 against 5.804 at 128), so the
individual cells are soft. The direction is not: counting's 1.012 bits against
the model's 0.240 is far outside anything one seed's wobble produces.
