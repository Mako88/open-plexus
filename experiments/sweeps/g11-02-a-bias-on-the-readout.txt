A bias on the readout
=====================

Script: experiments/g10_01_first_language.py --mode bias
Status: RUN. Two conditions, one seed. Local.

ANSWER: **two of five predictions, and the main one is REFUTED.** A bias does not
        reach the unigram and does not beat corrective writes. On
        `reward_recall` it is CATASTROPHIC, which the negative prediction caught
        and which matters more than the text number.

THE RESULT
-----------
    Tiny Shakespeare, width 64, chunk 256, cap 5.0, one seed

                        bits   accuracy
    Hebbian           5.4662     0.1756
    corrective        5.2556     0.1549
    **bias**          5.3115     0.1837
    unigram           4.8292     --

    reward_recall, first asks, width 64, floor 0.125

    **bias**           0.200     -0.456

PREDICTIONS, SCORED
--------------------
1. **REFUTED.** Bits do not fall below the unigram's 4.829. They reach 5.312,
   which is 0.48 short. The diagnosis was wrong: a missing prior was not what
   capped the model.

2. **REFUTED.** The improvement is 0.155 bits, LESS than corrective writes' 0.211
   and less than the 0.5 guessed.

3. **CONFIRMED.** Accuracy rises from 0.176 to 0.184, and it is the only cell
   where accuracy improved -- corrective writes lowered it.

4. **REFUTED, and this is the important one.** `reward_recall` was predicted to
   gain little or nothing. It **collapses**, 0.656 to 0.200, barely above the
   0.125 floor.

5. **CONFIRMED.** All 582 tests pass with the flag off.

WHY A PRIOR DOES NOT BUY THE PRIOR
------------------------------------
A bias alone would be a unigram. A bias PLUS a noisy retrieval is not, because
the retrieval term does not go away:

    answer = Wo @ retrieved + bias

To score like a unigram the model would have to IGNORE the retrieval, and it
cannot learn to -- both terms are trained together against the same error, and
nothing drives `Wo` toward zero where the store is uninformative. **Adding a
prior to a noisy signal gives the prior corrupted by the noise**, which is worth
0.155 bits rather than the 0.64 that separates the model from the unigram.

WHY IT DESTROYS `reward_recall`, WHICH IS THE REAL FINDING
------------------------------------------------------------
The bias learns the MARGINAL distribution of everything it is scored on. In
`reward_recall` that is 767 positions of which almost all are filler and cues,
and only a handful are the queried values. So the bias learns "expect filler",
and at a query position it adds a large constant favouring tokens that are never
the answer.

**This is the base rate, and note 013 already blamed exactly this for the
salience gate's apparent success.** It has arrived from the other direction: the
same statistic that flattered one mechanism destroys another.

So the honest account of a readout bias is:

> **It adds the marginal. That helps where the marginal is informative about the
> answer, and hurts where it is not — and neither case lets the model reach the
> marginal-only baseline, because the retrieval term keeps adding noise.**

Text is the first case, weakly. `reward_recall` is the second, severely.

WHAT THE NEGATIVE PREDICTION BOUGHT
-------------------------------------
Prediction 4 tested the DIAGNOSIS rather than the outcome, and it is the reason
this file says something useful. Had only Shakespeare been measured, 5.31 against
5.47 would have read as a modest win and the mechanism would have been kept,
defaulted on, and carried into the g9 line -- where it costs 0.46 of accuracy.

**A prediction that the mechanism should NOT help somewhere is worth more than
another prediction that it should.** That is the lesson to keep from this run,
above anything about biases.

RECOMMENDATION
---------------
**Do not default this on.** Keep the flag, off, for the text line only, and
never for `reward_recall` or any task whose answers are uniform by construction.
It is not a component improvement; it is a task-dependent prior with a large
downside.

Note 031's item (3) -- "the readout is the least examined component" -- is
answered in the negative for the first thing tried. The readout is not
underpowered for want of a constant term.


WHAT IT CHANGES
----------------
The readout computes `answer = Wo @ retrieved` with **no constant term**. So a
near-zero retrieval gives all-zero scores and a uniform distribution, and there
is no way for the model to express "e is common and q is not".

**A unigram baseline IS a bias over tokens.** g10-12 measured the model at 5.466
bits against a unigram's 4.829 and I called that "worse than ignoring context
entirely". That reading was right and the cause was not identified: the model
could not represent the thing it was losing to.

    answer = Wo @ retrieved + bias
    bias  += lr * (target - answer)

Each output unit's own prediction error, applied to itself. As local as the delta
rule beside it, so C1 is untouched.

**This is item (3) from [note 031](../../docs/notes/031-a-design-pass-against-the-goals.md)**,
which observed that the readout is the only component learning across sequences
and the only one no experiment has ever varied.


MEASURED ON
------------
- **bits per character** on Tiny Shakespeare, comparable ONLY with
  [g10-12](g10-12-the-standard-benchmark.txt)'s 5.466 and
  [g11-01](g11-01-corrective-writes.txt)'s 5.256 -- same corpus, split, width 64,
  chunk 256, cap 5.0, one seed, differing only in which flags are set.
- **`reward_recall` first-ask accuracy**, comparable only with the g9 line's
  ungated arm at the same width. It is a DIFFERENT task with a different floor
  and nothing in it may be compared with a bits figure.

The unigram and bigram figures quoted are from the same corpus and split, fitted
on the training text only.


PREDICTIONS
------------
1. **THE ONE THAT MATTERS: bits fall below the unigram's 4.829.** A bias alone
   can represent a unigram exactly, so a model that has one and also a store
   should not lose to a model that is only a prior. Confidence: high. If it does
   not clear 4.829 the diagnosis is wrong and something else is capping it.

2. **The improvement is larger than corrective writes bought.** That was 0.211
   bits. Guess: 0.5 or more, because a prior over 64 characters is a much bigger
   share of the remaining gap than an overwrite fix.

3. **Accuracy improves**, because an uninformed step can now guess the commonest
   character instead of index 0. Guess: from 0.155 to above 0.18.

4. **A NEGATIVE PREDICTION, to test the diagnosis rather than the outcome:
   `reward_recall` gains little or nothing.** Its answers are drawn uniformly
   from the value alphabet by construction, so a prior over values carries no
   information. If the bias helps THERE, it is not doing what this file claims --
   it would be papering over some other deficiency, and the account above is
   wrong even if the text number improves.

5. **Every existing test passes with the flag off.** Confirmed before writing
   this: 582 of 582.

Most likely wrong: 2. The store's contribution and the prior are not additive in
bits, and the readout may already be capturing some of the prior through
whichever retrieval directions correlate with frequency.


WHAT WOULD REFUTE WHAT
-----------------------
- bits still above 4.829         -> the missing prior was not the binding
                                    constraint and note 031's item (3) is
                                    answered in the negative
- `reward_recall` improves too   -> the mechanism is not doing what is claimed;
                                    see prediction 4
- accuracy falls                 -> the bias is dominating a retrieval that was
                                    carrying real information
