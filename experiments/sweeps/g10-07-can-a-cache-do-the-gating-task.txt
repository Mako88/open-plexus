Does a plain cache solve the task the whole g9 line is about?
=============================================================

Script: experiments/g10_07_can_a_cache_do_the_gating_task.py
Status: RUN. Counting only, three seeds, seconds, local.

ANSWER: yes, perfectly, at capacity 24 -- with no reward signal, no oracle, and
        48 integers. **In a cache the gate buys MEMORY, not accuracy. In the
        vector store it buys accuracy, because superposition degrades.** That
        sentence is what the g9 line has actually been measuring.


IN PLAIN TERMS
---------------
The test this project built its gating work around presents twenty-four
cue-and-item pairs and later asks about four of them. The device scores about
0.65 on those questions.

A lookup table that simply writes down all twenty-four scores 1.000. It is given
no hint about which four matter. It costs forty-eight numbers where the device's
memory costs four thousand.

So the difficulty the gating work has been measuring is not the difficulty of the
task. It is the difficulty of the storage that was chosen.


THE RESULT
-----------
    capacity   first-ask accuracy      what it means
           2                0.122      at the trivial floor of 0.125
           4                0.188      as many slots as there are rewarded pairs
           8                0.358
          16                0.674      about where the UNGATED MODEL sits
          24                1.000      one slot per binding presented
          64                1.000

    the model, same task: ungated about 0.65, oracle 1.000

**A cache of 24 answers it perfectly.** 24 is exactly `n_pairs` -- one slot per
binding the sequence presents. It needs all of them because, like the model, it
does not know which four will be asked about.

**A cache of 16 lands at 0.674, which is about where the ungated model sits.** So
the vector store at `d_model` 64 behaves roughly like a 16-entry table on this
task, while costing 4,096 numbers against 32.


THE REFRAMING, WHICH IS THE POINT
-----------------------------------
With a perfect gate you would need **4** slots, because only 4 bindings are ever
asked about. Without one you need **24**.

    in a CACHE          the gate buys MEMORY: 24 entries down to 4, a 6x saving
                        at identical accuracy
    in the VECTOR STORE the gate buys ACCURACY: 0.65 up to 1.000, because
                        superposition degrades as bindings accumulate

**Every recovery number in the g9 line is measuring the second thing.** The
oracle's advantage exists because 24 superposed bindings interfere; it does not
exist for a structure that keeps them apart. That does not make the g9 numbers
wrong — they are correct about the store they measure — but it does mean the
task never established that *selecting what to keep* is hard in general. It
established that superposition makes it necessary.


WHAT THIS DOES NOT SAY
------------------------
**It does not say the associative store is the wrong choice for the project.** It
says `reward_recall` does not discriminate between the two, and a benchmark that
does not discriminate cannot justify a mechanism.

Four things a cache does not do, none of which this task asks for:

1. **Generalise by similarity.** Superposition returns something for a key never
   seen; a table returns nothing. `reward_recall` only ever queries exact cues.
2. **Degrade gracefully.** A full table evicts; a store gets noisier. Which is
   preferable is a real question this does not touch.
3. **Slice by dimension.** The whole distribution story is a node holding part of
   every vector. A table shards by KEY instead -- which is a DHT, and is
   precisely John's third question rather than a dodge of it.
4. **Bind compositionally.** Nothing here needs it, and bAbI task 2 would.

**And the capacity pressure is real, not removed.** At capacity 4 the cache
scores 0.188. A bounded table that must evict without knowing the future faces
exactly the gating problem, in a different container. What changes is that the
pressure begins at 24 items rather than at the handful superposition tolerates.


PREDICTIONS -- REGISTERED BEFORE THE RUN
------------------------------------------
Written into the script before it ran:

    a cache answers the task        -> storing everything is enough, so
                                       SELECTING what to store is not required by
                                       the task, only by the vector store
    it does not                     -> the task is hard for a reason that is not
                                       about vectors

The first fired. I did not predict the capacity at which it would happen, and
would have guessed higher than 24 -- the number turning out to be exactly
`n_pairs` is the cleanest possible demonstration that nothing but raw capacity
was ever at stake.


WHAT WOULD REFUTE WHAT
-----------------------
- no capacity reaches 1.000       -> the task needs more than storage. NOT
                                     OBSERVED
- it needs far more than n_pairs  -> eviction order matters and the task has
                                     structure. NOT OBSERVED: exactly n_pairs
- a small cache matches the model -> the store is doing something a table cannot.
                                     PARTLY: 16 entries match it, at 1/128th of
                                     the memory
