What does a grounded question cost on a real link?
==================================================

Script: testbed/run.py --mode bucket --walk   (driver: tools/bucket_drive.py)
Status: RUN, local, 2026-07-31, Docker 29.6.1.

**The identity half is a CONTRACT and carries no predictions**, exactly as
`g35-01` says. The LATENCY was not predicted and is labelled as an incidental
measurement; a prediction for the obvious fix is registered below.

ANSWER: **the walk agrees with one process exactly, over containers, clean and
impaired — and one grounded question costs 10.2 seconds on a 40 ms link.**


IN PLAIN TERMS
--------------
`g35-01` sent the writing across real machines and checked the counts. It never
asked a question.

Asking is the part a person would actually wait for: start at a word, find what
belongs with it, follow the links, arrive at the picture. Every step means asking
the machine that holds that thing — and *that* machine then has to ask around
before it can answer, because judging whether two things belong together needs to
know how common each of them is.

The answers come back right. On a good connection a question takes about a
fourteenth of a second. On a connection with a realistic delay it takes **ten
seconds**.

Ten seconds is a long time to wait for one question, and it is worth being clear
about what is responsible. It is not the thinking; it is the number of small
messages and the fact that each one currently sets up a fresh connection before
it says anything. Both of those have known fixes that nobody has built.


WHAT IS BEING MEASURED
----------------------
    walk_agrees_with_one_process   every recovered class, against the same
                                   stream run in one process with the same
                                   statistic and the same derived bound
    rank_messages_per_walk         `RANK` messages the DRIVER sent
    seconds                        wall clock for the whole read phase

**A `RANK` is answered AT the owner.** The owner holds the row, fetches
`count(y)` from each candidate's owner itself, and returns a short list of ids.
The row never travels and the driver never gathers — a verb that returned a table
would be the collective C1 forbids, wearing a smaller payload.

So the driver's `rank_messages` is an undercount of total traffic: each one
causes the answering peer to send one `SEEN` per candidate, which is `g33-03`'s
per-partner cost arriving on a real link.


MEASURED ON
-----------
Docker 29.6.1, `testbed/Dockerfile`, four node containers plus a driver. `tc
netem` on every container including the driver.

    nodes            4
    bucket width    50
    tempo          100
    bound      derived      `g33-04`'s winner
    statistic conditional   the C1-safe one

Two shapes, because the impaired run is expensive:

    A   concepts 24, occasions 400, 73 surfaces, clean
    B   concepts  6, occasions  60, 19 surfaces, clean and at 40ms/10ms


PREDICTIONS
-----------
**None for the identity**, which is a contract: a walk over containers must
return the same classes as one process, and a count is not a matter of degree.

P1  CONNECTION REUSE IS WORTH MOST OF THE IMPAIRED TIME. Every message opens a
    socket, so each pays a setup round trip AND a request round trip. Holding
    connections should bring the 10.2s per walk under 6s — better than half,
    because the setup is a full RTT of the two.
    REFUTED IF it does not, which would put the cost in the message COUNT rather
    than the per-message overhead. Then the thing to attack is `g33-03`'s
    one-`SEEN`-per-candidate, which is a mechanism change rather than a
    transport one, and much larger.


COST
----
Shape A clean: 26.3s load, 10.54s walk. Shape B clean: 3.86s load, 1.36s walk.
Shape B impaired: 449.79s load, 193.65s walk. Image build excluded.


RESULTS
-------
    shape  link           surfaces  mismatches  walk agrees  ranks/walk  walk s
        A  clean                73           0         true         3.6   10.54
        B  clean                19           0         true         4.4    1.36
        B  delay 40ms/10ms      19           0         true         4.4  193.65

**`walk_agrees_with_one_process: true` in all three**, including under
impairment. So the read path — ranking at the owner, fetching marginals across
the network, checking mutuality from both ends — returns exactly what one process
returns.

    per walk, clean       0.072 s
    per walk, impaired   10.19 s        about 142x

**Mean class size at shape B is 4.05 where perfect recovery would be about 2.9,
and that is CORRECT rather than a defect.** It matches one process exactly, and
`occasions.py` already warns that a small world hands out accidental structure —
18 surfaces with an occasion of six is exactly the regime that caution names.
Shape A, four times larger, gives 3.47 and also matches.


WHAT THE 10.2 SECONDS IS AND IS NOT
-------------------------------------
**It is not the architecture's latency.** It is this implementation's, and the
two dominant terms are both known and both reducible:

  - **one connection per message**, named as a deliberate simplification at
    `bucket_peer.py`'s own definition and measured at 96x on the write path in
    `g35-01`. P1 above is registered against it;
  - **one `SEEN` per candidate partner**, which `g33-03` measured as scaling with
    FAN-OUT rather than with `k` — 439 reads for one walk at 192 surfaces.

**And it is worse than the figure John accepted.** `g24-01` measured 161 ms a
round over held connections and the ruling was that depth 10 at about 3.2 s is
acceptable because *"it's the internet, it's gonna be relatively slow"*. One
grounded question at 10.2 s is three times that, on a link half as bad.

So this does not overturn the ruling; it says the grounding read path is not yet
within it, and names the two things that would bring it there.

**What is still not measured**: the split between the driver's `RANK` messages
and the peers' `SEEN` fetches. Both were impaired and neither counted separately,
so which dominates is unknown — and P1's refutation clause is what would tell
them apart.
