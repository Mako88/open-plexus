Is the memory undertrained, or is it not a language model?
===========================================================

Script: experiments/g10_02_underfit_or_undertrained.py
Status: RUN. One cell, width 32, chunk 64, one seed, seven points on a curve.
        Local, minutes, no runner.

ANSWER: UNDERFITTING, at this width. It peaks at epoch ONE and gets worse after,
        and its best number on text it has ALREADY SEEN is 2.1 bits short of a
        bigram on the same text. More epochs buy nothing.


IN PLAIN TERMS
---------------
When something scores badly there are two very different reasons, and a single
number cannot tell them apart. Either it has not been given enough practice, or
it cannot do the thing at all. The fixes are opposite: more training, or a
different design.

The way to tell is to watch it practise, and to check how well it does on the
material it has already been shown. Something still improving needs more time.
Something that has stopped improving, and is still bad on material it has seen
before, has hit its own ceiling.

This one stops improving after a single pass, and never gets close on the
material it has seen.


WHY THIS RUN EXISTS
--------------------
[g10-01](g10-01-does-this-memory-beat-a-bigram.txt) registered `EPOCHS 2` as the
frozen axis most likely to be wrong, and registered this follow-up in advance:
*"if the result is negative, re-run one cell at many more epochs BEFORE
concluding anything structural."*

It is the cheaper question and it should arguably have been asked first.


THE RESULT
-----------
    uniform 6.426   unigram 4.756   bigram 3.711   bigram ON TRAIN 3.638

    epoch   train bits   test bits   test acc
        0        6.240       6.210      0.111     untrained
        1        5.780       5.847      0.159     the best it ever gets
        2        5.795       5.891      0.157
        3        5.809       5.932      0.132
        4        5.824       5.916      0.138
        5        5.779       5.843      0.154
        6        5.827       5.962      0.160

**It peaks at epoch 1 and then oscillates without improving.** Test bits fell
0.247 in total and *rose* 0.047 over the last two epochs. There is no trend left
to extract by training longer.

**And the training number is the decisive one.** On text it has already seen it
reaches 5.78 bits where a bigram fitted to that same text reaches 3.638. It is
**2.1 bits short on material it has memorised access to**, which is not a
generalisation failure and cannot be a budget failure.

The train and test curves also sit almost on top of each other -- 5.78 against
5.85 -- so there is no overfitting either. It is not learning the text and then
failing to transfer; it is not learning the text.


PREDICTIONS
------------
Registered in g10-01 before this ran, and scored here.

1. **"If the result is negative, more epochs might be the binding constraint."**
   **REFUTED.** Epochs are not the constraint. The curve is flat from epoch 1.

2. **Untested but now measurable: it does not beat the unigram.** 5.85 against
   4.756. Confirmed at this cell, and this was g10-01's prediction 2 -- the
   sharper and more damaging claim, and it holds.

3. Post-hoc, stated as such: the oscillation from epoch 2 onward, with training
   bits *rising*, looks like the store drifting rather than converging. Not
   measured here, and it is a candidate explanation rather than a finding.


RUN AGAIN AT WIDTH 128, AND THE CAVEAT BELOW IS NOW CLOSED
------------------------------------------------------------
The section below said this was one cell and that a wider node fitting the
training text would make the diagnosis width-limited rather than structural.
So the same curve was run at width 128, a FOURFOLD wider node:

    epoch      width 32              width 128
             train    test          train    test
        0    6.240   6.210          6.181   6.197
        1    5.780   5.847          5.785   5.826     <- both peak here
        2    5.795   5.891          5.781   5.883
        3    5.809   5.932          5.803   5.911
        4    5.824   5.916          5.801   5.844
        5    5.779   5.843          5.810   5.846
        6    5.827   5.962          5.817   5.956

**The two curves are the same curve.** Four times the width buys 0.005 bits on
training text at the epoch where each peaks. Both stop improving after one pass.
Both end 2.18 bits short of a bigram fitted to the text they have already seen.

**So the underfitting is not width-limited.** The caveat below is answered, by
measurement, at the width it named. Whatever is stopping this model is not the
size of the node -- which is the answer the tiny-node priority wanted, arriving
from the direction nobody hoped for: node size does not matter here because
nothing about the node is the binding constraint.

**What it still does not settle.** Both curves are at chunk 64. g10-01's re-run
is measuring chunk 256 across widths 32, 64 and 128 with the store capped, and
its partial cells show width buying 0.058 bits from 32 to 64 -- the same
near-nothing, on a different chunk. If its width-128 cells agree, the finding
holds on both context lengths tested.

WHAT THIS DOES NOT SHOW, AND IT IS A REAL LIMIT (as first written)
-------------------------------------------------
**This is ONE cell: width 32, chunk 64, one seed.** The script prints
"the conclusion is about the architecture", and that is stronger than one cell
can support. g10-01 is running width 128 and chunk 1024 as this is written, and
if a wider node fits the training text substantially better then the diagnosis is
**width-limited, not architectural**, and the sentence above is wrong.

The claim this run supports on its own is narrower and still worth having:
**at width 32 the model underfits character-level English, and the epoch budget
is not what is stopping it.**


COST
-----
Local, seven evaluation points, minutes. No runner, no matrix. A diagnostic
exists to tell two explanations apart and a grid would not tell them apart
better.
