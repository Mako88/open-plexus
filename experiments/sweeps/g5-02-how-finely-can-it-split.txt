How finely can a fixed capacity be divided, and does that get harder?
=====================================================================

Script: experiments/g5_02_how_fine.py
Status: RUN on Actions, 90/90 cells. **THE MAIN QUESTION IS NOT RESOLVED**
        -- the exponent lands at 0.50 with a resolution of +/-0.50, which
        spans g1-10's 0.37. But it settles something more important:
        **g5-01's wall dissolves at machine width 32**, so G5's 'does not
        pass' verdict is WITHDRAWN. And the summariser committed the same
        error as g5-01's, one sweep later, in the tool written to stop it.


IN PLAIN TERMS
--------------
g5-01 found a wall: with machines of 16 slots each, adding more of them stopped
helping on the longest problem. Sixteen machines got 0.769 where the bar is 0.90,
and doubling from eight to sixteen bought two percentage points.

Re-reading an earlier experiment answered why. The same 128 slots of capacity
score 0.741 when split into eight machines and **0.992** when split into four.
Identical capacity, identical problem -- only the size of each piece differs. So
the wall is about how SMALL each machine is, not how many there are.

That turns the question into a much better one. Take a fixed amount of capacity
and cut it into more and more pieces. At some point it breaks. **Does that
breaking point get worse as problems get harder?**

If it does, then this whole approach buys scale by making machines BIGGER rather
than by adding MORE of them -- which for a system meant to run on ordinary
computers scattered across the internet is the thing that matters most.


QUESTION
--------
Hold total width at 256. Split it P ways -- so each machine gets 256/P
dimensions -- and find the largest P that still reaches 0.9.

  total width  256 (fixed)
  P            1, 2, 4, 8, 16, 32   -> machine width 256, 128, 64, 32, 16, 8
  seq_len      96, 192, 384
  lr           0.01, 0.02, 0.05, 0.1, 0.2
  seeds        1, 2, 3
  budget       8 epochs

**8 epochs, not 16, and that is a measurement rather than a saving.** g5-01
checkpointed every arm at 8 and 16 and nothing moved by more than 0.014, so the
second half of its budget bought nothing anywhere. Costed: 11.7 hours serial, 90
jobs, worst job 13 minutes.

At fixed total width, P and machine width are the same variable seen from two
ends. That is deliberate: it removes the confound that made g5-01 hard to read,
where growing the network grew the capacity at the same time.


WHAT IS ALREADY KNOWN, AND WHY IT IS NOT ENOUGH
------------------------------------------------
  seq 192   machine width 16 works (g5-01: 0.993 at sixteen machines)
  seq 384   machine width 16 fails (0.769), machine width 32 works (0.992)

Two points, at factor-of-two resolution, from two different sweeps. They are
consistent with the minimum machine width doubling when the sequence doubles --
an exponent of **1.0** against the **0.37** that g1-10 measured for TOTAL width --
and they are equally consistent with anything from about 0.5 upward. That gap
matters enormously and cannot be closed by staring at the existing numbers.


PREDICTIONS -- written before the run
--------------------------------------
1. **The largest usable P falls as the sequence lengthens.** Guess: 32 or more at
   seq 96, about 16 at seq 192, about 8 at seq 384. That is a halving per
   doubling.

2. **So minimum machine width grows with an exponent near 1.0**, far worse than
   the 0.37 for total width. Guess: 0.8 to 1.0.

3. **Therefore the number of useful machines is roughly FIXED, not growing.**
   Total width needed grows as T^0.37 and machine width as T^0.8-1.0, so their
   ratio -- the machine count -- *shrinks*. **This is the decisive G5 statement
   and it is unfavourable:** past some problem size you cannot buy capability by
   adding machines, only by making each one bigger.

4. **P=1 solves every length tested** (256 undivided, against g1-13's crossing of
   46.8 at seq 384). The ceiling control: if P=1 ever fails, the total width is
   too small and every P above it is measuring the wrong thing.

Most likely wrong: (2). If the exponent comes back near 0.37 -- machine width
scaling like total width -- then machine count is roughly constant with problem
size rather than shrinking, which is a materially better world and the one to
distrust. **Check before believing:** that the crossings are not all pinned to
one grid point, and that P=1 is genuinely at ceiling rather than being rescued by
a lucky learning rate.


WHAT WOULD REFUTE WHAT
-----------------------
- max P falls with seq_len             -> confirms the wall is machine width and
                                          quantifies how fast it closes. G5's
                                          refutation stands and is now specific
- max P is flat across seq_len         -> machines compound after all; g5-01's
                                          wall was an artefact of growing the
                                          network and the problem at once
- max P is 32 everywhere               -> the grid does not reach the breaking
                                          point; nothing is measured and finer
                                          splits are needed
- P=1 fails anywhere                   -> the ceiling control fails; 256 is too
                                          narrow for that length and its row must
                                          be dropped


WHAT THIS DOES NOT SETTLE
--------------------------
Whether a different DECOMPOSITION escapes the wall. Every machine here owns a
contiguous block, chosen once, holding a fixed slice of one shared memory. Nothing
tests overlapping assignments, machines that specialise, or hierarchical grouping
-- and the wall is a fact about this decomposition rather than about distributed
computation.

Nor does it revisit bandwidth. If machines must be large, note 009's affordable
region tightens, since its `d . rate` product uses the FULL width for the key
broadcast regardless of how it is split.


RESULT
------
Total width 256 throughout, 3 seeds, each arm at its own lr. Pooled / alone.

  seq_len 96      P=1  1.000/1.000   P=2  1.000/1.000   P=4  1.000/0.999
                  P=8  1.000/0.997   P=16 1.000/0.953   P=32 1.000/0.779
  seq_len 192     P=1  1.000/1.000   P=2  1.000/1.000   P=4  1.000/0.999
                  P=8  1.000/0.994   P=16 0.992/0.890   P=32 0.938/0.665
  seq_len 384     P=1  1.000/1.000   P=2  1.000/1.000   P=4  1.000/0.999
                  P=8  0.999/0.911   P=16 0.758/0.615   P=32 0.661/0.459

  ceiling control: P=1 reaches 1.000 at every length, so every cell measures
  division rather than capacity


THE HEADLINE, AND IT RETRACTS THE PREVIOUS ONE
------------------------------------------------
**At seq_len 384, eight machines of 32 dimensions each score 0.999 pooled and
0.911 alone.** Both clear the bar.

g5-01 concluded that machines stop compounding at 384 steps and this project
recorded G5 as the first gate that does not pass. That conclusion was drawn from
a grid that pinned machine width at 16, and **16 is below the minimum at that
length.** The wall was a property of the chosen machine size, not of
partitioning.

  **G5's "does not pass" is withdrawn. G5 is UNRESOLVED.**

What survives from g5-01 is narrower and still true: *at a fixed machine width of
16, adding machines stops helping past 192 steps.* That is a real constraint --
machines cannot be arbitrarily small -- but it is not the claim that was made.


WHAT IS ACTUALLY MEASURED
--------------------------
Minimum machine width, by the `alone` criterion, which is the one C1 needs since
it describes a machine that cannot afford to pool:

    seq 96    16       usable machine count 16
    seq 192   32       usable machine count 8
    seq 384   32       usable machine count 8

Minimum width does grow. Whether it grows fast enough to matter is the question,
and **this grid cannot answer it**: widths are resolved only to a factor of two,
over a lever arm of 4x in sequence length, giving

    exponent 0.50, resolution +/-0.50, so anywhere in [0.00, 1.00]

g1-10's exponent for TOTAL width is 0.37, which sits inside that range. At the
low end the usable machine count is constant and partitioning scales freely; at
the high end it falls as T^-0.63 and the approach is bounded. **Those are
opposite conclusions and this experiment distinguishes them not at all.**


THE PREDICTIONS
----------------
1. **Largest usable P falls as sequences lengthen -- HELD in direction.** By the
   `alone` criterion 16, 8, 8; by `pooled` at least 32, at least 32, then 8.
   Guessed 32/16/8. Falls, but the two criteria disagree about when, and the
   pooled row is floor-limited at two lengths.

2. **Exponent near 1.0 -- NOT SCORED.** The measurement is [0.00, 1.00]. This was
   flagged before the run as most likely to be wrong; it is neither confirmed nor
   refuted, which is a third outcome the note did not anticipate.

3. **Usable machine count roughly fixed or shrinking -- NOT SCORED**, for the
   same reason. This was billed as "the decisive G5 statement" and it remains
   undecided.

4. **P=1 solves every length -- HELD.** 1.000 at all three, so the ceiling
   control passes and every cell measures division rather than capacity.

Two of four predictions turned out to be unanswerable by the grid designed to
answer them. **The design error was choosing factor-of-two width steps to measure
a quantity whose interesting range is a factor of two wide.**


THE TOOL DID IT AGAIN
----------------------
The summariser printed, for two of three rows:

    largest usable P: 32 <- AT THE EDGE OF THE GRID, breaking point not located

and then fitted an exponent through those two rows anyway, reporting

    MINIMUM MACHINE WIDTH grows as seq_len^1.00
    USABLE MACHINE COUNT SHRINKS as problems grow

**That is the same failure as g5-01's, one sweep later, in the tool written to
prevent it.** g5-01's version dropped a length that failed to cross; this version
kept two lengths whose crossing was a floor. Both flagged the problem in prose
and computed through it.

The general shape, now stated where it belongs:

  > **A caveat printed next to a number does not attach to the number.** If a
  > value is a bound, the code has to refuse to use it as a value.

Three fixes: rows at the grid floor are excluded from the fit rather than
annotated; the exponent is reported with the resolution the grid can actually
support, rather than as a point; and the learning-rate check runs per row instead
of pooled across rows -- pooled, a single interior choice anywhere cleared a grid
that was pinned in every individual comparison.

That last fix immediately found something: **seq 96's row is pinned at the bottom
of the lr grid, all six arms at 0.01.** It is benign here, because that row is at
1.000 everywhere and ties resolve to the first value, but the pooled check had
been reporting the whole sweep as clean.


WHAT WOULD RESOLVE IT
----------------------
- **A finer width grid.** Steps of 2x cannot measure a quantity that moves by 2x
  across the range tested. Widths of 12, 16, 20, 24, 32, 40 would.
- **A longer lever arm.** 96 to 384 is 4x. Reaching 1536 would quadruple the
  span, and matters more than resolution: the same factor-of-two uncertainty over
  16x in length gives +/-0.25 instead of +/-0.50.
- Both are one sweep, and the second is expensive: seq 1536 at width 256 costs
  roughly four times the longest cell here.
