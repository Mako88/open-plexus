G0 step 1 -- what does knowing nothing score?
=============================================

Script: experiments/g0_01_baselines.py
Status: RUN. Predictions 1, 2, 3 and 6 held. Predictions 4 and 5 REFUTED, and
        the refutation is the useful part -- the base rate is NOT the floor.


IN PLAIN TERMS
--------------
Before we can say a system has learned anything, we need to know what a system
that has learned nothing scores. If guessing gets you 50% and our clever method
gets 52%, that is not a result -- but without the first number it looks like one.

This also runs several deliberately stupid strategies that should NOT work. If
one of them does work, the test is accidentally easy in some way we did not
intend, and we would rather find that out now than after building a model
against it.

And it runs a cheat: a solver that is simply told the answers. That one must
score 100%. If perfect knowledge cannot answer the question, the question is
broken -- which is exactly the defect the very first generated sequence had.


QUESTION
--------
What do non-learning strategies score on MQAR, across every difficulty dial, and
is the task answerable at all in each configuration?

400 sequences per condition, one dial moved at a time from a fixed reference
(n_pairs=4, seq_len=64, n_keys=32, n_values=8).


PREDICTIONS -- written before the run
--------------------------------------
1. oracle = 1.000 in EVERY condition, exactly. Any other value means the task is
   ill-posed there and every number in that row is void. This is the whole
   reason the oracle is in the harness.

2. base ~= 1/n_values. Concretely 0.125 at the reference (n_values=8), 0.500 at
   n_values=2, 0.250 at n_values=4, 0.0625 at n_values=16.
   Values are drawn uniformly, so the most common one should have no meaningful
   edge beyond sampling noise. If base sits well ABOVE 1/n_values, the generator
   has a value-distribution imbalance nobody intended.

3. rand ~= base, both near 1/n_values. Where they differ, the difference IS the
   imbalance in (2), and is worth seeing rather than assuming away.

4. recent ~= base. Queries are placed at random offsets well after the pair
   block, so the most recent value token seen is essentially unrelated to the
   key being queried. If recent is clearly above base, recall distance is too
   short and the benchmark is not testing retention.

5. posn ~= base. Query order is shuffled independently of pair order. If posn is
   clearly above base -- and especially if it approaches 1.0 -- the shuffle is
   not working and the task can be solved by counting rather than by recall.

6. base, recent and posn are all roughly INDEPENDENT of n_pairs, seq_len and
   filler. Only n_values should move the base rate. If filler moves it, filler
   is leaking into the answers.

The prediction most likely to be wrong: (2) at n_pairs=1, where only one query
per sequence is scored and the sampling noise on 400 draws is much larger.


WHAT WOULD REFUTE WHAT
-----------------------
- oracle < 1.000 anywhere        -> generator defect, task unanswerable
- base >> 1/n_values             -> value sampling is not uniform
- recent >> base                 -> recall distance too short to test retention
- posn -> 1.0                    -> query order leaks pair order
- base moves with filler         -> filler is correlated with the answers

HELD
----
1. oracle = 1.000 in every one of the 13 conditions. The task is answerable
   everywhere it was asked. This is the check that would have caught the
   ill-posed generator mechanically rather than by someone reading output.
2. base tracks 1/n_values closely: 0.134 vs 0.125, 0.510 vs 0.500, 0.260 vs
   0.250, 0.072 vs 0.062. Slightly high throughout, which is the mode of a
   finite uniform sample and not an imbalance worth chasing.
3. rand ~= base everywhere.
6. base, recent and posn are all completely flat against filler and seq_len --
   identical to three decimals. Only n_values and n_pairs move anything.


REFUTED, AND THIS IS THE FINDING
---------------------------------
4 and 5 both said the shortcut baselines would sit near the base rate. They do
not. At the reference they score 0.349 and 0.346 against a base rate of 0.134 --
**2.6x the base rate** -- and at n_pairs=1 they score exactly 1.000.

The cause, worked out after the run and then checked:

  Filler is drawn from spare KEYS, so the only value tokens anywhere in a
  sequence are the n_pairs pair values. A strategy that emits any value it has
  already seen is correct whenever it happens to name the queried pair, or when
  another pair carries the same value by chance.

That gives a closed form:

  floor = 1/n_pairs + (1 - 1/n_pairs)/n_values

Checked against both shortcut baselines across all eight non-degenerate
conditions: worst deviation 0.016. It fits.

WHAT THIS CHANGES
- The bar a model must clear is 0.344 at the reference, not 0.134. Reporting a
  model at 0.30 against "a base rate of 0.134" would have described being
  beaten by a one-line heuristic as a success.
- n_pairs sets the floor. Note 006 established that multi-query is what makes
  the task discriminating at all; this adds an independently measured second
  reason for the same dial. At 4 pairs the floor is 0.344, at 16 it is 0.180.
- n_pairs=1 is degenerate: floor = 1.000 exactly. Diagnostic use only. It must
  never carry a result, and MqarConfig.trivial_floor now says so where a reader
  would be standing.

The prediction flagged in advance as most likely wrong -- (2) at n_pairs=1 --
was fine. The two nobody doubted are the ones that broke.


A VACUOUS TEST, FOUND BY THE HARNESS
-------------------------------------
Adding mutations for the baselines turned up a survivor:
`constant-baseline-not-fitted` replaces "most common value" with "smallest value
id", and the entire suite stayed green.

Because values are uniform, every constant scores about 1/n_values. Accuracy is
pinned by the value distribution rather than by which value was chosen, so no
accuracy-based assertion could ever see the difference. Rule 9's failure mode
exactly: an assertion on a quantity that something else holds fixed.

Fixed by asserting the contract on deliberately skewed data, where the mode and
the minimum differ. 11/11 mutations now caught.
